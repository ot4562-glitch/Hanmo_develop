# Hanmo Develop — 아키텍처

> 현재 유효한 제품 및 기술 설계입니다. 실제로 구현된 기능과 앞으로 구현할 목표를 구별합니다.  
> **이 문서는 변경 이력이나 회의록이 아닙니다.** 설계가 바뀌면 이전 안을 남기지 않고 현재 안으로 수정합니다.

## 1. 프로젝트 목표

한모를 **수강신청할 때만 방문하는 모의연습 사이트**에서 **입학 후 수강계획부터 졸업까지 지속적으로 이용하는 비공식 학업 플랫폼**으로 확장합니다.

- **포함:** 학기별 강의·분반·담당교수, 시간표·대체과목, 학점·재수강·이수요건, 주전공·이중전공·부전공, 수강신청·전공신청·학사공지·학사일정, 졸업시험·논문·인증·졸업사정, 학적·학점교류, 강의 개설 전망·학업 경로.
- **제외:** 고용·취업·진로·채용·직무 멘토·NCS, 실제 학교 수강신청 자동화, 학교 계정 인증 대행, 공식 졸업사정의 대체.
- **일관성:** 기존 BASIC / TIME / SELECT 모의신청의 화면·조작 충실도를 지키며, 개인별 학사 판단은 검증된 공식 규정이 있을 때만 근거와 함께 안내합니다.

## 2. 개발 단계 및 책임 범위

| 단계 | 우리 팀의 완료 목표 | 기존 한모 코드 | 외부 DB |
|---|---|---|---|
| **1차 — 학업 플랫폼** | 독립 추가 페이지·계산 엔진·입력/저장·테스트 완성 | **수정 금지** | 없이 작동 |
| **2차 — 실전 모의신청** | 기존 연습화면에서 선택형 실패·대체검색·재접속 시나리오 완성 | **원개발자 협의 및 승인 후** 변경 | 없이 작동 |
| **3차 — 데이터 연동** | Supabase DB·수집·검증·갱신·보안·배포 설계 **및 인계 완료** | 별도 협의 | **우리 팀은 개설·운영하지 않음** |

우리 팀은 **1·2차의 실제 구현과 검증**에 집중합니다. **3차의 Supabase 프로젝트 개설·소유·운영 및 실제 서비스 연동은 임창용 님과 협의**하고, 우리 팀은 바로 실행에 옮길 수 있을 정도의 설계와 인수 기준만 전달합니다. 2차의 기존 페이지 변경 및 최종 병합·배포에도 원개발자 승인이 필요합니다.

## 3. 시스템 구성

\`\`\`text
[1·2차: GitHub Pages만으로 실행·검증]
기존 한모 BASIC / TIME / SELECT
    └─ 2차: 승인받은 선택형 실패·복구 시나리오

독립 /degree-rescue/ 추가 페이지
    ├─ HTML/CSS + 브라우저 TypeScript 번들
    ├─ 학점·전공·졸업·시간표·개설 전망 계산 코어
    ├─ 검증된 정적 JSON/CSV와 사용자 직접 가져오기
    └─ 브라우저 로컬 학업계획·체크리스트·백업

[3차: 완전한 설계만 인계 / 현재 미연결]
한국외대 공개 학사자료
    → 허용된 수집 → 변경 감지 → 검증·승인
    → Supabase PostgreSQL (구조화 정보와 필요한 이력)
    → 읽기 API / 동일한 데이터 계약
    → /degree-rescue/ 추가 페이지
\`\`\`

**프런트엔드와 계산 분리:** React 의존 화면은 정적 HTML/DOM으로 변환하고, TypeScript의 순수 계산 함수는 데이터 저장 방식과 분리합니다. 1·2차는 JSON/CSV 어댑터만으로 실행되어야 하며, 향후 DB 조회 어댑터를 교체해도 계산 코드가 달라지지 않도록 합니다.

**코드 자산:** HUFS One AI의 학사 관련 핵심 계산·계약·참조 코드 및 테스트는 \`degree-rescue/\` 내부에 보존합니다. \`legacy-academic/\`의 React·Fastify·PostgreSQL 코드는 **참조용**이며 번들에 포함하지 않습니다. 다른 저장소에 대한 빌드·개발 의존성을 만들지 않습니다.

**개인 자료:** 실제 이수현황·시간표·계획·학업 체크 항목은 기본적으로 브라우저 메모리·IndexedDB/로컬 저장 및 사용자 파일 백업으로 처리합니다. 학교 로그인·개인 원본 성적 데이터는 원격 서버로 자동 전송하지 않습니다.

## 4. 1차 — 수강에서 졸업까지의 추가 페이지

기존 \`index.html\`, \`html/\`, \`js/\`, \`css/\`, \`img/\`, \`CNAME\` 및 원래 모의신청 화면·포커스·키보드·시간 계산을 **수정하지 않습니다**. 추가 기능은 \`degree-rescue/\` 독립 주소에만 구축하고, 원본 사이트 메인 메뉴도 건드리지 않습니다.

### 4.1 학업 현황과 졸업요건

- **학생 조건:** 캠퍼스·입학년도·주전공·이중전공/부전공·학적 상태·목표 졸업학기.
- **이수 원장:** 취득 완료/수강 중/계획/인정 미확정 학점을 구분. 전공·교양 영역, 필수/선택필수·선수 교과, 중복 인정 제한, 재수강·학점포기·동일/대체 교과목을 계산합니다.
- **비학점 요건:** 졸업시험/FLEX, 논문·대체 제출물, 외국어 인증, 졸업 신청·사정·증명/서류, 등록학기, 졸업대기/수료를 별도로 표시합니다.
- **전공 What-if:** 주전공 변경, 이중전공 추가·변경·포기, 부전공 추가·변경·포기에 따른 부족 과목·학점·예상 이수경로를 비교합니다.
- **장기 계획:** 남은 요건과 학기별 개설 가정·학점 상한·선수과목을 합쳐 향후 **2~4학기의 시간표와 졸업 경로**를 탐색하는 기능을 목표로 합니다. 현재 한 학기 제약 검사 코어와는 다른 신규 최적화 작업입니다.

학칙은 **입학년도·캠퍼스·전공/학과·교육과정 적용 기간별 RulePack**으로 관리하고, 공식 자료가 없거나 기준이 충돌하면 \`확인 필요\`로 표시합니다. 학점 충족만으로 졸업을 확정하지 않습니다.

**학칙 개정의 개인별 영향(1차 목표):** 승인된 이전/다음 RulePack을 같은 학생 이수 원장에 적용해 안정적인 요건 ID별 추가·폐지·변경, `충족→미충족`·`미충족→충족`과 필요한 추가 이수를 보여줍니다. 기존 `rule-diff.ts` 코어를 활용하지만 판본 승계·적용 범위·공식 조항·적용일이 미확인되면 판단을 보류합니다. 과목의 영역 배분이 바뀌었다면 새 분류 원장이 없는 비교 결과는 미확정입니다. 공식 졸업 판정이나 소급 적용 확정을 의미하지 않습니다.

**학생용 흐름:** 학생 이수 내역 → 학번·전공별 규정과 검수 여부 → 부족·확인 필요 요건 → 관련 강의/신청·제출/공지·학사 담당 부서. 계산 코어와 학생 화면 연결은 진행 중이며 JSON 입력 시연만으로 완료라고 판단하지 않습니다.

### 4.2 강의·담당교수·시간표

- **검색:** 과목명·학수번호·학기·분반·학점·개설학과·담당교수 표시명·요일·시간·강의실·캠퍼스.
- **이력:** 과목 식별과 개설 학기·분반·담당교수 배정을 분리합니다. 과거에 같은 과목이 여러 교수/시간으로 개설됐을 수 있으며, 강의시간표의 표시명은 공식 인사 DB와 다릅니다.
- **입력:** 공식 출처가 검증된 JSON/CSV 또는 사용자가 직접 저장한 WIS 강의시간표를 로컬에서 가져와 형식·중복·학기·출처를 확인합니다.
- **계획:** 시간표 충돌·학점 상한·선수 요건·필수 이수영역을 검증해 수강 우선순위, 시간표 **A/B/C안**, 유효한 대체 과목을 제안합니다. 공식 인정 여부는 별도 규정 확인이 필요합니다.

**계산 결과의 판본 일관성(1차 필수):** 결과마다 `rulePackVersion`, `ledgerVersion`, `catalogVersion`, `planVersion`, 원본 확인 시각과 `asOf`를 기록합니다. 규정·강의/폐강·개인 이수 내역·계획의 판본이 달라지면 이전 결과를 `STALE / 재검토 필요`로 무효화하고 재계산 전에는 현재의 유효한 추천처럼 표시하지 않습니다. 입력 JSON의 판본 문자열만으로 검증을 증명할 수 없습니다. 기존 `study-plan.ts`의 판본 필드를 이용하되, UI에서의 자동 무효화는 남은 개발 목표입니다.

### 4.3 학사공지·학사일정·졸업 체크리스트

**학생의 졸업 목표 → 미충족 요건 → 필요한 수강·신청·제출 → 적용되는 공지와 마감**이 이어지도록 설계합니다.

| 영역 | 일정/공지 | 계획과의 관계 |
|---|---|---|
| 수강 | 사전신청·본신청·정정·철회, 개설/폐강·계절학기 | 필수과목 및 대체 시간표 |
| 전공 | 주전공/세부전공 선택, **이중전공 신청·변경·포기**, 부전공·전공심화 | 졸업요건·다음 학기 과목 |
| 졸업 | 졸업시험·논문·외국어 인증, 졸업사정·서류·학위수여 | 비학점 요건 및 제출 마감 |
| 성적 | 성적 조회·정정, 재수강·학점포기·학점교류 인정 | 취득학점 및 졸업 가능 시점 |
| 학적·등록 | 휴학·복학·재입학·초과학기 등록 | 남은 등록학기 |
| 학업 지원 | 학사 FAQ·교환학생·교직·학습상담 | 학업·졸업에 직접 관련된 절차 |

공지별 **캠퍼스·입학년도·전공·학적·목표 졸업학기·남은 요건**을 판정하고, 정보가 부족하면 \`대상 확인 필요\`로 둡니다. **공지 게시일을 신청 마감일로 추측하지 않습니다.** 학생 접수 마감과 행정 보고 마감은 분리하며 모든 시각은 Asia/Seoul 기준입니다. 정정/취소·출처 불명 자료는 검토 상태를 표시합니다.

학생별 **이번 학기 해야 할 일, 실제 확인된 D-day, 졸업 체크리스트**를 제공합니다. 개인 체크는 메모이며 학교 승인·공식 졸업 판정이 아닙니다.

**졸업요건–공지 연결:** `openRequirementIdsFromAudit`로 미충족·검토 필요 요건을 파악하고 공지의 `requirementRefs`에 연결합니다. 안정적 요건 ID와 규정 판본이 다르거나 공지의 학생 적용 범위를 확인할 수 없으면 확정 매칭을 하지 않습니다. 학생 직접 입력 또는 정적 학점 계산에서 도출한 ID는 **로컬 후보**에 불과하므로 관련 공지를 위로 올리는 힌트로만 사용하고, 후보가 없다는 이유로 다른 공지를 숨기거나 공식 충족으로 바꾸지 않습니다. 현재 별도 페이지 간 전달은 동일 탭에서 요건 후보 ID·규정 판본·계산 시각만 넘기는 방식이며 실제 학교 검수 원장과의 연동은 미완료입니다.

**학생별 일정 우선순위와 달력:** 확인된 접수 마감 7일 이내, 미충족 요건과 관련된 공지, 적용 범위 미확인 공지, 일반 정보를 구별합니다. 미검수 파일의 기한은 참고용 입력 시각으로만 표시하고 검증된 긴급 알림으로 승격하지 않습니다. 중요 공지의 상단 제한 고정과 달력 보기는 목표 기능이며 정정/취소 판본이 과거 공지보다 우선합니다.

**근거 중심 학사 FAQ:** 정적 한국어 검색과 응답 검사를 활용해 문장·수치·날짜마다 출처 판본·대상 조건·학교 담당 부서 링크를 함께 제시합니다. 근거 없는 합격/지원 자격 확정이나 실제 상담 예약 제공을 금지합니다. 교환학생·국제학생 체크리스트와 검증된 다국어 번역은 선택적 확장입니다.

### 4.4 역사적 개설 근거와 조건부 전망

- 과거 동일 계절 학기의 강의 개설·미개설, 분반·담당교수 변경과 공식 확정 자료를 구분합니다.
- **과거 자료가 누락된 학기 ≠ 미개설 학기**입니다. 데이터 범위와 완전성을 명시합니다.
- "과거 4회 중 3회 개설"은 **관측 이력**이지 "다음 학기 개설 확률 75%"가 아닙니다. 보정된 확률은 충분한 공식 이력과 백테스트 후에만 검토합니다.

- **반복 학사행사 예상 구간:** `campus-assist/activities.ts`의 연도별 개최 기록을 활용합니다. 서로 다른 연도의 검수된 개최 자료가 최소 2개이며 개최 시기 분산이 제한된 경우에만 대략적 예상 구간을 계산합니다. 취소·정정·출처 권리가 불명확하거나 분산이 크면 보류합니다. 이 구간을 확정 신청 마감이나 D-day로 표현하지 않습니다. 계산 코어는 존재하지만 학생 일정 UI 연동은 아직 목표입니다.
- 미개설·수강 실패·전공 변경·휴복학·교환학점 인정을 가정했을 때 부족 학점·우선과목·목표 졸업학기가 어떻게 달라지는지 재계산합니다. 전공 선발 합격 가능성은 필요한 검증 자료 없이는 추정하지 않습니다.

## 5. 2차 — 기존 모의수강신청 실전 시나리오

**원개발자 승인 후 별도 PR로 개발합니다.** 기본 BASIC/TIME/SELECT는 그대로 유지하고 사용자가 원할 때만 돌발상황을 실행합니다. 독립 새 연습 페이지가 아니라 **기존 연습 페이지와 입력 흐름의 선택형 확장**이 목표입니다.

### 5.1 마지막 강좌 신청 실패 (LAST COURSE FAIL)

1. 목표 N개 과목과 예비 대체 강좌를 설정합니다. 연습 데이터는 합성 강좌가 기본입니다.
2. 재현 가능한 훈련에서는 처음 N−1개의 신청이 성공하고 마지막 목표 1개가 **가상 정원 마감** 등의 사유로 실패합니다.
3. 학생은 연습을 종료하지 않고 **직접 다른 과목을 검색·선택·모의신청**합니다.
4. 시간/학점/선수요건/이수영역/기신청 강좌와 충돌하면 무효입니다. **대안이 없는 상황을 정확히 확인하는 것**도 올바른 대응입니다.
5. 원래 목표 달성·대체 확보·미해결·잘못된 대체 선택으로 결과를 나눕니다.

### 5.2 튕김·재접속 (RECONNECT RECOVERY)

- 진입 직후, 일부 신청 후, 확인창 대기 등 설정한 시점에 **가상 세션 단절**을 만듭니다.
- 학생이 모의 재접속·대기열·진입을 수행하고 **성공 확인/결과 불명/미신청 과목**을 구분합니다.
- 결과 불명 신청은 성공으로 간주하거나 중복 신청하지 않습니다. 실제 학교 사이트에 접근·자동 로그인하거나 네트워크를 끊지 않습니다.
- 정원 마감·긴 대기열·충돌·취소 실수·복합 위기 등 난이도를 추가할 수 있습니다.

**평가:** 단순 클릭 속도보다 복구 성공, 유효한 대체과목, 실패 인지 및 대응 시간, 실수·중복 신청, 검증된 학업계획 영향이 우선입니다. 시나리오 ID/난수 시드를 고정해 반복 재현합니다.

**시뮬레이션과 실제 강의의 경계:** 가상 수강신청 과목 코드와 공식 과목/분반 ID 사이의 연결은 명시적인 변환 계약으로만 수행합니다. 연습의 성공·취소·대기열은 실제 수강 확정이나 학점 취득을 뜻하지 않으며 이수 원장에 반영하거나 학교 시스템으로 전송하지 않습니다.

## 6. 1·2차 자료·검증·배포 원칙

- **출처 검증:** 공식 URL, 확인일, 적용 대상·기간, 학칙 판본과 `SYNTHETIC`·`REFERENCE_ONLY`·`SOURCE_REVIEWED`·`NEEDS_REVIEW`를 구분합니다. URL·검토 날짜·`SOURCE_REVIEWED` 필드를 JSON 파일 안에 적는 것은 **자체 선언**이지 운영 검수의 증거가 아닙니다.
- **검수 권한 분리:** 사용자 업로드·로컬 계산·단순 정적 참고 목록은 미검수로 받아들입니다. 검수된 학생 마감이나 공지를 제공하려면 별도 운영자가 원문·판본·대상·정정 이력을 확인한 배포 자산이 필요합니다. 현재 일정 코어는 입력 JSON 필드와 별도로 **검수된 데이터 객체 참조**를 전달받아야 검수된 공지로 인정합니다. 업로드 제공자는 스스로 그 참조를 만들 수 없습니다. 3차는 검수자와 승인자 권한, 승인 기록·철회·원문 해시를 관리합니다.
- **결과 신뢰성:** 사용자 학점·학칙 JSON은 계산 가능해도 공식 졸업 판정의 증거가 아닙니다. 출처·규정·원장·강의/계획 판본이 일치해야 사용하고 변경되면 계산을 무효화하며, 불명확한 적용 대상과 누락은 `확인 필요`로 남깁니다.
- **접근 범위:** 학교의 공식 API 및 공개 자료 접근/재사용 권한을 확인하며, 보호된 로그인/SSO를 우회하지 않습니다. 학교 시스템 오류나 확정 결과를 재현한다고 과장하지 않습니다.
- **개인정보:** 학생 성적 원본·학교 계정·비밀키를 공개 GitHub에 넣거나 자동 전송하지 않습니다. 브라우저 자료의 삭제/백업을 제공하고 공유 PC 이용을 안내합니다.
- **테스트:** 학점·전공·학칙·이중전공·공지 범위/KST 기한·학기 개설·시간표 제약·가상 복구에 대한 회귀/속성 테스트, 정적 빌드·브라우저 사용성·접근성 확인.
- **원본 보호:** 1차에서 기존 한모 프로그램 파일의 변경은 **0건**. 2차는 원개발자 승인 후에도 기본 모드의 포커스·키보드·시간·결과가 바뀌지 않아야 합니다.
- **권리:** 원본 한모의 GPL-3.0, HUFS One AI 팀 기여 코드 공개 재배포 권리, 학사자료 수집·사용 권리를 실제 병합·배포 전 확인합니다.

## 7. 3차 — Supabase 설계 인계

**아래는 앞으로 넘길 목표 아키텍처입니다. 실제 Supabase 프로젝트·자동 수집·DB 연동은 아직 구축하지 않습니다.** 원문 PDF/HTML/첨부파일은 저장하지 않고 필요한 구조화 정보와 **원문 링크·변경 이력**만 관리합니다.

### 7.1 핵심 데이터 계약

| 논리 테이블 | 필요한 정보 |
|---|---|
| \`courses\` | 학수번호, 이름, 학점, 이수영역, 동일/대체과목 연결 |
| \`course_offerings\`, \`sections\` | 학기, 캠퍼스, 개설 상태, 분반, 담당, 요일/시간, 장소 |
| \`faculty\`, \`teaching_assignments\` | 공개 교수 표시명·소속, 학기별 강의 담당 이력 |
| \`academic_notices\`, \`notice_revisions\` | 원문 식별자·URL, 게시 부서/표시, 게시·수정시각, 핵심 추출 내용, 대상, 정정/취소 |
| \`academic_events\` | 시작·신청/제출마감·시험일, 캠퍼스·학번·전공 대상 |
| \`graduation_rules\`, \`program_requirements\` | 전공/입학년도별 이수학점·필수과목·논문·시험·언어 인증·규정 판본 |
| \`data_sources\`, \`sync_runs\` | 출처·확인일·변경 해시 및 수집 상태 |
| \`source_reviews\`, \`review_approvals\` | 검수·승인자 역할, 자료 판본·해시, 검수/승인/철회 시각과 감사 기록 |
| \`data_snapshots\` | 강의·학칙·공지 판본 묶음, 유효 기간, 무효화 상태 (학생 개인정보 제외) |
| \`event_series\`, \`event_occurrences\` | 반복 학사행사 계열, 확정 개최·변경/취소·예상 구간과 근거 분리 |

- 데이터는 과목과 학기별 개설·분반, 교수와 담당 이력을 분리해 중복을 줄입니다. 공지 원문을 매번 복제하지 않고 변경된 판본만 보존합니다.
- 무료 DB **500MB는 실사용량·인덱스·행 오버헤드 측정 전 용량 보장치가 아닙니다**. 필요한 저장량·성장률·상위 요금제 이관 방안을 인계 설계에서 명시합니다.
- 학생 개인 이수·성적/계획은 기본적으로 로컬에 보관하며, 다중 기기 동기화는 별도 개인정보·인증 검토 후 선택형으로 설계합니다.

### 7.2 데이터 갱신 아키텍처

\`\`\`text
공식 공개 학사자료 또는 허가된 API
  → 정기 수집(GitHub Actions / 승인된 워커)
  → 원문 식별자·수정일·해시로 변경 감지
  → JSON/CSV 핵심 필드 정규화와 규정·일정 검증
  → 검수·승인 → 현재값 및 필요한 이력 DB 반영
  → 공개 읽기 전용 API → 학업 플랫폼
\`\`\`

학교가 공식 API 또는 자동 수집 권한을 제공하지 않는 경우 **실시간 자동 갱신을 보장하지 않습니다**. 오류·누락·취소·정정에 대비해 확인 시각, 보류 표시, 재시도와 **정적 JSON 대체 경로**를 둡니다.

### 7.3 인계에 반드시 포함할 산출물

- DB 스키마/관계도, 예시 데이터, 키·인덱스·변경판/규정 기간, SQL 마이그레이션 설계, 용량·비용·백업/복구.
- 공개 읽기 권한과 수집/검수 쓰기 권한 분리, RLS·보안 정책, 비밀키의 클라이언트 노출 금지.
- 자료 출처별 접근/재사용 조건, 갱신 주기, 수집 실패·정정/취소 처리, 검수자와 운영 점검.
- GitHub Pages 데이터 어댑터 전환, API 장애 시 로컬 대체, 테스트·배포·롤백 및 운영자 인수 체크리스트.
- 임창용 님의 프로젝트 개설·소유·운영·비용 승인, 원개발자 코드 병합과 데이터 사용 권한을 명시한 전달 문서.

## 8. 완료 판단과 현재 상태

| 단계 | 통과 조건 |
|---|---|
| **1차** | DB 없이 추가 페이지가 실제 사용 가능하고 계산·로컬 데이터·브라우저 QA를 통과. 원본 프로그램 불변, 공식 자료 부족은 미확인 처리 |
| **2차** | 승인된 기존 화면 확장과 실패/재접속 회귀 테스트 통과. 시나리오 미선택 시 기존 모드 동작 불변 |
| **3차** | 실연동 없이도 소유자가 개설/구현을 판단할 수 있는 DB·수집·API·보안·운영·전환 설계가 준비됨 |

**현재:** 기존 한모는 운영 중이고 학업 추가 기능은 미병합 개발 PR에 있습니다. 학교 전체 강의/학칙 정본, 실제 Supabase 데이터베이스와 자동 갱신은 연결되지 않았습니다. 계획과 실서비스 구현 완료를 구분해야 합니다.
