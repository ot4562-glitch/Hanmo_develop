## 1. 프로젝트 목표

한모를 **수강신청할 때만 방문하는 모의연습 사이트**에서 **입학 후 수강계획부터 졸업까지 지속적으로 이용하는 비공식 학업 플랫폼**으로 확장합니다.

- **포함:** 학기별 강의·분반·담당교수, 시간표·대체과목, 학점·재수강·이수요건, 주전공·이중전공·부전공, 수강신청·전공신청·학사공지·학사일정, 졸업시험·논문·인증·졸업사정, 학적·학점교류, 학칙 개정 영향, 강의 개설·학사행사 전망, 근거형 학사 FAQ, 학업 상담 경로, 교환학생·국제학생 학업 준비.
- **제외:** 고용·취업·진로·채용·직무 멘토·NCS, 실제 학교 수강신청 자동화, 학교 계정 인증 대행, 공식 졸업사정의 대체.
- **일관성:** 기존 BASIC / TIME / SELECT 모의신청의 화면·조작 충실도를 지킵니다. 학생에게는 **현재 부족한 것, 근거, 다음에 할 일, 불확실성**을 함께 제시하며, 학사 판단은 검증된 규정과 적용 대상이 확인되는 범위에서만 안내합니다. 계산 가능·소스 이식·화면 작동·공식 검증·출시 적합은 별도 상태입니다.
- **현재 UI와 기능 우선순위 (#113~#116, 사용자 승인):** 학점 정리는 `졸업 준비`의 [학점]/[졸업요건] 탭으로 통합하고, `강의 전망`은 `강의 검색` 결과에 포함합니다. 학사 달력·FAQ·공식 상담은 검수 전에도 날짜 격자·공식 경로를 살펴볼 수 있는 탐색 화면으로 시각화하되 공식 일정·점수·요건을 꾸며내지 않습니다. BASIC 돌발상황에는 **가상 정원 마감(CAPACITY, 기본 OFF)**만 오늘 추가하며 404(RECONNECT)와 나머지 TIME/SELECT는 기존 경로를 유지합니다. 정원 마감 시 `register.png` 버튼을 제거하고 전공·교양·기초의 **합성 대체과목** Search를 제공하지만, **실제** 대체과목 추천·시간표 충돌·공식 분반/정원 정보는 자료 권리·독립 검수 전까지 보류합니다. NEXT/LAST_VALID·응답 지연·세션 만료·대기열 증가 구현은 포함하지 않습니다.

### 1.1 학생에게 내세울 세 가지 차별화 경험

|---|---|---|

**대외 안내의 사실성 계약 (#38):** 외부 소개에는 “내 전공 공지를 찾고, 다음 학기 수강신청을 미리 준비하는 곳”을 설명 문구 후보로 사용하되, **현행 홈·학업 페이지에 별도 대형 홍보 카드나 반복 소개 문구를 다시 넣지 않습니다**. 세 차별점은 **현재 제공 / 합성 시연 / 예정 / 검수 자료 필요** 중 한 상태를 기능별로 명시하고, 과거 개설 횟수는 미래 확률로, 행사 예상 구간은 공식 접수일로, 가상 복구 훈련은 실제 학교 네트워크 장애로 표현하지 않습니다. 외부 비교표는 기능·확인일·공식 링크·실제로 확인한 사용 흐름이 있는 경우에만 작성하고 “최초/유일/무조건 성공” 표현은 객관적 증거 전까지 금지합니다. 학생 사용성 과제는 (A) 확정/전망/검수 필요를 구별하는가, (B) 근거를 실제로 열어보는가, (C) 실패 후 상태 확인·재접속을 판단하는가로 나누어 성공률과 오해 사례를 기록합니다. 경쟁 기능 미확인은 ‘없음’이 아닌 ‘확인 안 됨’으로 둡니다.

**연결된 사용 흐름:** ② 과거 개설 관측 → 다음 학기 수강계획과 대안 작성 → ③ 예상 학사행사 구간에서 준비할 일 확인 → ① 가상 404·재접속 훈련으로 계획을 점검합니다. 학사공지 **예측**은 공식 공지가 발표되기 전의 대비 수단이며, 공식 정정·취소/확정 공지가 있으면 항상 이를 우선합니다.

**구현 자산과 대외 주장:** ②·③은 앞서 HUFS One AI 학업 모듈에서 개발된 개설·행사 전망 접근법을 **선별 검토·재사용할 수 있는 후보**입니다. 한모에 검증된 과거 전수 자료, 출시 가능한 UI, 공식 데이터 승인 및 소스 재배포 권리가 모두 확보되었다는 의미는 아닙니다. 현재 조사만으로 “국내 최초”, “유일”, “학교·비공식 어디에도 없는 기능”을 객관적으로 확정할 수 없으므로, 외부 홍보에서는 구체적 기능 차별화를 설명하고 절대적 독점 표현은 별도 비교 검증 후에만 사용합니다. ### 1.2 첫 학생용 출시 범위

대외적으로 설명할 핵심 목적은 **“내 전공 공지를 찾고, 다음 학기 수강신청을 미리 준비하는 곳.”**입니다. 현재 홈페이지는 기존 한모의 공지·시간·모의신청 버튼을 유지하므로 이 문구를 홈의 별도 대형 안내 블록으로 렌더링하지 않습니다. 학생이 개설 근거를 찾고, 예상 준비 기간과 학교가 확정한 마감을 구분하고, 연습에서 실패 뒤 알맞게 대처하는지를 검증합니다. 유사 서비스 비교는 기능·출처·확인일을 기록해 [#38](https://github.com/ot4562-glitch/Hanmo_develop/issues/38)에서 완료합니다.

### 3.1 실행 경계

- **정적 우선:** 새로운 학업 계산·NLP·검색·학생용 데이터 연계 로직은 **JavaScript + JSDoc**가 원본입니다. 기존 HUFS One AI 선별 이식 소스와 신규 로직도 JavaScript/JSDoc으로 통일하고 TypeScript 파일은 새로 추가하지 않습니다. 빌드 출력물이 아니라 유지보수 원본을 JS로 바꾸고, Zod/예외/출처·저장 계약과 원본 동작을 비교합니다. React 의존 화면이나 외부 DB 필수화를 도입하지 않습니다.
- **2차 언어 경계:** 기존 시뮬레이터의 시나리오는 **JavaScript·기존 HTML/CSS로 직접 구현**합니다. React나 TypeScript 개발환경을 기존 페이지의 필수 의존성으로 도입하지 않습니다. 1차 코어와 연동이 필요하면 빌드된 JavaScript 공개 어댑터 및 명시적 입력/출력 계약을 사용하며, 학생 이수 원장이나 외부 DB 원본을 시뮬레이터에 결합하지 않습니다.
- **3·4차 전환 경계:** 기존 TS→JS/JSDoc 이전은 **3차 실연동과 독립적으로 완료**했습니다. 순수 함수·공통 계약·예측/NLP·학업 코어·앱/뷰·테스트를 JS로 통일했으며, 이전 결과·예외·자료 상태의 전체 동등성은 추가 검증 대상으로 남습니다. 3차의 새 코드 역시 JS로 작성하고, 4차에서 **잔여 TS 0개·전체 정적/브라우저·보안·Supabase 인수**를 최종 확인합니다. SQL/RLS·운영 도구의 언어는 기술상 적절한 형식을 유지합니다.
- **단일 진실의 출처:** 공식 확인을 주장하는 자료는 운영 검수된 릴리스 자산과 그 판본·해시에서만 채택합니다. 형식 검증에 통과한 사용자 파일은 비공식 자료입니다. 학교 자료를 자동 갱신하지 못하는 경우 마지막 검수시각을 표시합니다.

- **첫 적용 대상과 검수:** **서울·글로벌캠퍼스, 2010학년도 입학생부터, 모든 전공**을 1차 대상 범위로 정합니다. 캠퍼스·입학년도·전공별로 학점·전공필수·졸업시험·논문 등 요건의 정본·시행일·경과 규정을 대조합니다. 개인 졸업 진단은 독립 검수·승인을 마친 조합부터 제공합니다. 대상 범위 안의 미확보·미검수 조합도 ‘확인 필요’로 표시하고 다른 입학년도·전공의 요건을 대신 적용하지 않습니다. [#11](https://github.com/ot4562-glitch/Hanmo_develop/issues/11)
- **RulePack 키:** 캠퍼스·학번 범위·주/이중/부전공·입학전형·교육과정/트랙·적용 시작/종료·규정 버전. 같은 조건에서 승인된 규정이 둘 이상 충돌하거나 예외의 적용 범위가 확정되지 않으면 자동 선택을 중단합니다.
- **원문 재현성:** 학칙 조항·단서·예외·각주를 빠짐없이 독립 목록으로 만들고 `sourceSpanRef`, 원문 URL·해시, 조항 ↔ `requirementId` 양방향 연결과 숫자 일치 여부를 확인합니다. 원문 목록 자체를 후보 RulePack과 동일한 도구가 생성했다면 독립 검수가 아닙니다.
- **승인 게이트:** 검수자와 승인자를 서로 다른 역할로 두고 적용 시점·공개 시점·검토 시각·원문 판본·범위·개정 승계 관계를 확인합니다. `APPROVED` 문자열이나 사람 이름을 사용자 JSON에 넣었다고 실제 승인이 되지 않습니다. 문제가 있으면 기존 검증 판본을 유지하거나 '확인 필요'로 처리합니다.
- **개정 비교:** `rule-approval.js` 및 `rule-diff.js`의 개념을 채택합니다. 안정적인 `semanticKey`/요건 ID를 전제로 같은 학생 이수 원장을 개정 전·후 RulePack에 적용해 `ADDED / REMOVED / CHANGED / UNCHANGED`와 `GAINED / LOST / SAME / UNKNOWN`을 구분합니다.
- **변경 영향 화면:** 학생에게 '새 필수과목', '충족 → 미충족 가능', '면제/대체 인정 변경', '추가 확인/이수 필요', '적용 대상 아님/불명'을 근거 조항과 함께 설명합니다. 학사 적용일·학번 소급 규정은 임의 해석하지 않습니다. 과목의 영역 재분류가 바뀌었다면 새로운 분류 원장(`nextAttempts`)이 없는 경우 결과를 확정하지 않습니다.
- **판본 역행 방지:** 이전 규정의 충족 결과를 새로운 규정으로 그대로 복사하지 않습니다. 개정 체인 단절·중복/겹침·승인되지 않은 규정·규정 ID 변경을 발견하면 차이표를 보류하고 학생에게 확인할 원문을 제공합니다.

### 4.3 강의·교수 표시·시간표·계획 스냅샷

- **검색:** 학수번호·과목명·학기·캠퍼스·분반·학점·개설학과·요일/시간·강의실·담당교수 **표시명**. 단, **요일·시간·강의실·담당교수·분반 상세 검색은 현재·예정 학기와 최근 3개 학년도**로 한정하며, 더 오래된 학기는 **과목별 실제 개설 여부·검증된 분반 수·관측 범위·출처**만 검색할 수 있습니다. 과거 분반 상세를 이용한 시간표 검색 기능은 만들지 않습니다. 과목 고유 식별자, 분반/개설 학기, 수업 담당 이력을 분리합니다. WIS 수동 저장 HTML/CSV의 형식·중복·학기·범위·출처를 검증합니다.
- **강의 검색의 순위·안전:** 학수번호·분반·학기 정확 일치 → 과목명/교수 표시명 → 오타·띄어쓰기·약칭 후보 순으로 검색합니다. 캠퍼스·개설학기·동일/대체과목 관계는 독립 검수 전 확정하지 않습니다. **현재 승인 공개 강좌 연동은 비활성**이며 합성 강좌 4개는 #95에서 제거했습니다. #53·#40의 통합 검색 품질 계약은 후속 인수 대상입니다.
- **자료 사실성:** 로컬 WIS 저장본에 나오는 교수 이름은 해당 수업의 표시명이지 재직·인사·지도교수·연락처/강의평가 정본이 아닙니다. 사용자 제공 CSV는 형식 검사를 통과해도 `UNVERIFIED`입니다. 과목 코드에서 분반을 자동 분리하거나 제목만으로 동일 교과목이라고 추정하지 않습니다.
- **로컬 파일 계약:** 저장한 WIS HTML과 정해진 형태의 CSV를 받고, 학기·캠퍼스·코드·빈 값·중복을 검증합니다. 기존 8개 컬럼(`courseCode, courseName, credits, category, major, semester, campus, cohort`)과 원래 강좌 코드를 유지해 검증된 행만 UTF-8 CSV로 내보냅니다. 교수 이름·인원·개인정보는 제외합니다. CSV 가져오기 화면과 입력 오류 시험은 [#43](https://github.com/ot4562-glitch/Hanmo_develop/issues/43)에서 검증합니다.
- **수강계획 검증:** 한 학기 학점 상한, 선수요건, 시간표 충돌, 인정 영역, 이미 들은 과목, 분반 개설 상태를 함께 검사합니다. 확인된 분반이 없으면 강의·시간을 가상 생성하지 않고 `확인 필요`로 남깁니다. 대체 과목은 공식 동등성·학칙 범위가 확인되어야 '인정 가능'이라고 표기합니다.
- **계산 스냅샷:** 학칙 `rulePackVersion`, 이수 원장 `ledgerVersion`/`transcriptVersion`, 강의·분반 `catalogVersion`, 사용자 계획 `planVersion`, 행사·공지 자료 `noticeSnapshotVersion`, `asOf`, 적용 조건 및 출처 목록을 결과마다 결합합니다. 판본·시간표·폐강·정정·규정 승인/철회 중 하나라도 바뀌면 이전 결과는 `STALE / 재계산 필요`가 되며 저장된 추천을 재사용하지 않습니다.
- **재현성:** 동일 스냅샷과 동일 입력은 동일 결과를 내야 합니다. 단순 파일명/문자열 버전이나 로컬 체크 상태는 공식 소스의 최신성/승인을 증명하지 않습니다. 버전 하나가 누락되면 그 자료를 참조한 결과만 안전하게 보류하고 잘못된 부분 갱신을 막습니다.

### 4.4 학사공지·신청기간·미충족 요건에서 행동까지

**학생 → 규정·이수 원장 → 미충족/확인 요건 → 필요한 과목·신청·제출 → 적용 공지·실제 마감 → 담당 부서/원문 확인**을 하나의 사용자 흐름으로 연결합니다.

| 영역 | 공지 및 행동 | 연결할 학생 조건 |
|---|---|---|
| 수강 | 사전신청, 본신청·정정·철회, 계절학기, 개설·폐강 | 부족 과목·분반·학점 상한·선수 요건 |
| 전공 | 주전공/세부전공, 이중전공 신청·변경·포기, 부전공·전공심화 | 학번·학적·전공 조합·지원 조건 |
| 졸업 | 졸업시험/FLEX, 논문, 외국어 인증, 사정·제출 서류·수료·학위 | 비학점/학점 요건·목표 졸업학기 |
| 성적·학적 | 성적 정정·재수강·학점포기·학점교류 인정, 휴·복학·등록 | 원장 인정 상태·학적·등록학기 |
| 국제·지원 | 교환학생 지원·학점 인정, 학사 FAQ, 교직/학업 상담 | 언어·이수학기·캠퍼스·관련 교육과정 |

- **공지 출처 계약:** 공지 ID/개정 ID, 게시/정정/취소 시각, 작성 부서, 원문 URL, 학생 적용 범위, 학생 접수 마감 `studentDeadline`, 행정 보고 마감 `adminDeadline`, 시험/행사일, 공지 유형·학기, 근거 요건 `requirementRefs`·과목 `courseRefs`를 구분합니다. 게시일은 접수 마감일이 아니고 행정 마감은 학생 D-day가 아닙니다. 모든 날짜는 `Asia/Seoul`로 표시·계산합니다.
- **학생 대상 판정:** 캠퍼스·학번·전공 역할·학적·졸업 목표·요건별 상태 중 필요한 값이 없으면 `UNKNOWN`; 명확히 불일치하면 `NO`; 충분히 확인되면 `YES`. 자기 입력 졸업 목표만으로 공식 졸업예정자 신분을 추정하지 않습니다.
- **공지 후보 추출 코어(#99 병합):** `notice-extract.js`가 원문에서 캠퍼스·학번·학생 구분, 학생/행정 기한·행사일·정정/취소 표현을 **근거 위치가 있는 후보**로 반환합니다. `CANDIDATE`는 학교의 검수/학생 대상 확정이 아니고, 모호한 내용은 `NEEDS_REVIEW`, 사용 불허는 `EXCLUDED`로 분리합니다. **합성 코어 CI만 검증, 실제 자료·학생 UI 미연결.** #27·#41·#42·[#46](https://github.com/ot4562-glitch/Hanmo_develop/issues/46)·[#99](https://github.com/ot4562-glitch/Hanmo_develop/pull/99)
- **요건 자동 연결:** `openRequirementIdsFromAudit`와 공지 `requirementRefs`를 연결하되 **동일한 검증 RulePack의 요건 ID**여야 합니다. 학생이 직접 적거나 정적 계산에서 도출한 '미충족 후보'는 공지를 찾아주는 힌트일 뿐 '공식 충족/비대상'을 판정하지 못합니다. 후보가 없다는 이유로 필수 공지나 검토 필요 공지를 숨기지 않습니다.
- **공지 정정/취소:** 동일 ID 판본 충돌·미래 게시·철회/취소·권리 회수·출처 불명은 격리하고 과거의 확인된 공지를 무조건 되살리지 않습니다. 동일 제목 여러 개를 하나의 확정 마감으로 합치지 않습니다.
- **중요도 모델:** 검수되고 적용 대상이 `YES`인 필수 공지 중 **학생 마감 7일 이내**를 최우선(`CRITICAL_DUE`), 그다음 학업 필수(`ACADEMIC_REQUIRED`), 학생 관심/직접 관련(`PERSONAL`), 일반(`GENERAL`)로 분류합니다. 미검수 후보는 검토 목록으로 분리하며 확인된 필수 공지로 격상하지 않습니다. 지난 마감은 '기한 경과·담당부서 확인'으로 표시하고 상단 고정 대상에서 제외합니다.
- **검색 주제 분류 ≠ 학생 대상 확정:** 검색어가 전공·졸업·학점 관련 단어와 유사하더라도 그 사실만으로 학생 적용 대상 `YES`나 `CRITICAL_DUE`를 판정하지 않습니다. 검색 주제 분류 혼동/오탐은 #40, 근거 있는 공지 적용·마감 분류는 #51의 별도 검증 게이트로 둡니다.
- **상단 고정/캘린더:** 검수된 공지 중 학생에게 해당하고, 정확한 학생 마감이 남아 있으며 **7일 이내**인 필수 공지를 중요도·마감순으로 **최대 2건** 고정합니다. 적용 여부와 자료 검수 상태는 별도 값으로 관리합니다. 대상이 불명확하거나 자료가 미검수인 공지는 '원문 확인 필요' 목록에 노출하고 원문 링크를 제공합니다. 달력은 '개최일/시험일', '학생 신청 마감', '사용자 개인 목표' 표식을 구분합니다. [#51](https://github.com/ot4562-glitch/Hanmo_develop/issues/51) · [#58](https://github.com/ot4562-glitch/Hanmo_develop/issues/58)
- **개인 졸업 체크리스트:** 14개 항목의 자기 점검과 공식 규정 기반 충족 판정을 **별도 열/상태**로 표시합니다. 수동 `DONE`은 '본인이 확인함'에 불과하며 학교의 이수·인증 완료를 뜻하지 않습니다. 각 행의 미충족 요건·근거 공지·준비 행동·확인 부서로 탐색할 수 있도록 합니다.

### 4.5 강의 개설 전망 및 반복 학사행사 예상 구간

**학생 경험의 목표:** 공식 개설 발표 전에 과거 같은 시즌의 개설 패턴으로 수강계획과 대체안을 미리 작성하고, 졸업시험·이중전공 신청/변경 등 반복 행사의 **준비 예상 구간**을 개인 학업 달력에 참고 표시합니다. **예측은 실제 개설 보장이나 학교 확정 신청 시작·마감 알림이 아닙니다.** 확인 가능한 과거 관측·원문 링크·표본·신뢰 수준을 함께 설명합니다.

- **강의 개설:** 같은 시즌의 과거 개설·미개설을 관측값으로 사용하고 공식 확정 공지·개설 목록은 가장 높은 우선순위로 별도 표시합니다. 누락된 학기를 미개설로 채우지 않으며 관측 범위/완전성을 표기합니다. `k/n`을 곧바로 미래 확률 `k/n × 100%`로 표시하지 않습니다. 가정 변경·rolling-origin 백테스트를 통과하지 않은 확률 보정은 보류합니다.
- **관측 원장:** 사용권·검수가 허용한 **2010년 이후** 출처·판본·캠퍼스·학기·수집 범위별로 `개설 확인`, `미개설 확인`, `미관측`, `과목 식별 불명`을 장기 보존합니다. 최근 3개 학년도가 지난 분반의 요일·시간·강의실·담당 상세는 정리하지만, 학기별 개설 판정·**관측된 분반 수(전체 수 보증 아님)**·완전성·최초 확인 판본과 시점을 유지합니다. 목록에서 빠졌다는 이유로 미개설을 판정하려면 해당 과목을 포함하는 캠퍼스·학기의 목록이 완전하다는 근거가 있어야 합니다. 미관측·식별 불명은 `k/n` 분모에서 제외하고 별도 표시합니다. 코드 변경과 동일·대체과목 관계에는 유효 기간과 근거 판본을 기록하고, 검증된 동일 과목 관계에 한해 개설 관측을 연결합니다.
- **시점 재현 평가:** rolling-origin의 각 예측 기준 시점에 공개되고 검수가 끝난 판본만 사용합니다. 이후 정정·취소는 해당 시점의 입력에 소급 적용하지 않습니다. 같은 시즌 개설 빈도와 직전 같은 시즌 관측을 기준선으로 비교하고, 제공률·보류율·판정 오류를 캠퍼스·시즌별로 남깁니다. 행사 예상 구간은 적중률과 구간 폭을 함께 기록합니다. 운영 기준은 검수 골드셋의 관측 범위와 재현 결과로 정합니다. [#41](https://github.com/ot4562-glitch/Hanmo_develop/issues/41)
- **반복 학사행사:** `campus-assist/activities.js`가 제공하는 행사 계열(교내 학사 행사/전공 신청/졸업시험 등)의 과거 개최일을 연도별·공식 원문별로 묶습니다. 서로 다른 **최소 2개 연도**의 유효한 개최 근거가 있어야만 계절성 구간을 추정합니다. 현행 이식 코어는 개최일 분산 **45일 초과 시 보류**, 전후 **약 7일 여유**의 대략적 기간을 생성하는 휴리스틱입니다. 이는 학교의 공식 예정일/신청 시작·마감일이 아닙니다.
- **정정/취소 우선:** 해당 연도의 검증된 일정·취소·정정이 예측보다 우선합니다. 날짜 없는 취소가 어느 회차를 가리키는지 불명확하면 예측을 중단합니다. 출처 권리·검증일·대상 계열·과거 연도 간 충돌을 확인해야 하며, 자료가 불충분할 때 인위적인 D-day를 만들지 않습니다.
- **학생 표시:** `확정된 행사일`, `과거 이력 기반 예상 구간`, `근거 부족/취소 확인 필요`를 다른 시각/문구로 보여줍니다. 예상 구간에는 신청 버튼·확정 마감 알림을 연결하지 않고 공식 공지를 확인하도록 유도합니다.

### 4.6 근거 중심 학사 FAQ·교내 학사 상담 안내

**로컬 저장·백업의 구현 계약 (#17·#45, 1차 설계 결정):**

## 5. 2차 — 기존 모의수강신청 실전 시나리오

BASIC 오른쪽 아래 **돌발상황**은 `RECONNECT`(1회 가상 404)와 `CAPACITY`(BASIC에서 무작위로 한 과목의 정원 마감) 두 예/아니오를 각각 기본 OFF로 제공합니다. CAPACITY가 ON이면 마감된 강좌 신청 버튼이 사라지고, Search를 누르기 전 라디오만으로 관심강좌·전공·교양·기초의 조회 조건을 바꿀 수 있습니다. Search를 누르면 전공·교양·기초는 합성 대체과목만 보여줍니다. 실제 강의 정원·신청 서버·실학사 자료와 연결하지 않으며, RECONNECT/접속 대기/원본 신청 버튼의 기본 동작을 보호합니다. [#116](https://github.com/ot4562-glitch/Hanmo_develop/issues/116)

**접속 대기 시간 세부 설정 (사용자 결정, PR #109):** 필수 SETTING의 기존 단일 접속 대기 예/아니오를 **'강의 신청에 적용할까요?' (예/아니오, 기본 예)**와 **'수강신청 페이지 접속 시에 적용할까요?' ### 5.2 전환 시점의 가상 404·실제 브라우저 복구 (RECONNECT)

- **발생 시점:** BASIC 모드에서 옵션 ON → 원본 `practice.html` 실행 → 기존 시작 대기/원본 `selectZone.html` 진입 → 새 정적 `incident-404.html`로 **1회 이동**. 선택만으로 즉시 404를 띄우거나 0~6초 타이머로 중간에 보여주지 않습니다. 실제 HTTP 응답은 정적 페이지 **200**이며, 학교 시스템·실제 네트워크 오류가 아닌 UI 모의 훈련입니다.
- **화면:** 수강신청 좌측 바는 원본과 유사한 시각 상태로만 보여 주고, `inert`/모든 버튼 disabled/키보드 포커스 제외로 클릭·Enter·Tab 활성화를 차단합니다. 오른쪽 정상 신청표·탐색·신청/삭제 버튼·기존 타이머는 모두 **숨긴 새로운 페이지**로, 가상 404 메시지와 브라우저 복구 안내만 남깁니다.
- **복구:** 페이지 내 버튼 없음. **지원하는 복구 안내는 Chrome 실제 새로고침(F5/브라우저 UI)뿐**이며, 감지 시 토큰을 소비하고 정상 `selectZone.html`로 `location.replace`합니다. 오류 화면에는 **'브라우저의 새로고침을 사용하세요.'**라고만 표시합니다. 브라우저 뒤로가기는 기록·캐시 상태에 따라 동작이 달라 **지원하거나 복구 방법으로 안내하지 않습니다**. 기존 뒤로/앞으로 캐시 상태 소비는 무한 오류 재진입 방어로만 유지합니다. `practice` 진입은 기존 `location.replace` 계약을 유지합니다.
- **신뢰 경계:** `sessionStorage`의 일회성 BASIC 토큰(선택·원본 practice 진입·전환 확인)은 다른 모드·직접 URL·만료/변조 상태에서 거부합니다. 초기 전환 30분, 오류 화면 새로고침 복구 유효성 5분을 상한으로 하되, 유효하지 않은 직접 오류 화면 접속은 정상 `selectZone`으로 복구합니다. 새 브라우저 탭의 최초 진입은 기본 OFF이나, 같은 탭에서 **확인**을 눌러 선택한 예/아니오는 독립된 `hanmo.synthetic404.selection.v1` 세션 키로 유지합니다. 메뉴로 돌아오거나 다시 로드해도 이전 선택을 표시하며, 취소로는 변경되지 않습니다. 선택 저장 키와 전환 토큰을 구분해 404는 새 BASIC 시작 시에만 다시 1회 발생하고, TIME/SELECT 실행이나 오류 복구가 선택 자체를 삭제하지 않습니다. 브라우저 세션이 끝나면 초기 OFF로 복귀하며 저장소가 차단되면 기본 OFF로 시작하고 장애 주입을 포기해 원본 연습으로 안전하게 진행합니다.
- **진입 버튼 버그:** `index.html`의 연습 버튼은 시간 제한 안내 중에도 표시·모드 선택 화면까지 이동할 수 있습니다. 기존 모의신청 실제 연습의 09:58~10:10 제한은 그대로이며, 이를 404 또는 메뉴 선택 기능으로 우회하지 않습니다.

[인계 문서](student-data-source-handoff.md)


**아래는 목표 아키텍처이며 Supabase 프로젝트·자동 수집·DB 연동은 아직 구축하지 않았습니다.** 2026-11-19 사용자 확인에 따라 **Supabase는 Free 플랜($0) 범위에서만 운영**하고, **임창용 님이 프로젝트·계정·운영을 관리**하며, **장애 발생 시 개발팀이 함께 신속히 진단·복구**합니다. 유료 플랜 전환·유료 애드온·초과 사용료가 발생하는 서비스는 제품 설계 범위에서 제외합니다. 실제 계정 접근권·보안 키·복구 연락망은 프로젝트 생성 시 점검하되 운영 책임자를 다시 미정으로 취급하지 않습니다. 학사 원문 PDF/HTML/첨부파일을 DB에 통째로 저장하지 않고 권한이 확인된 **구조화 정보·근거 링크·필수 변경 이력**만 관리합니다.

**3차는 두 개의 완료 게이트를 구분합니다.** 팀 설계 인계와 운영자의 실제 Supabase 연동·검증은 별개입니다. **코드 언어 통일은 3차 실연동 전에 진행할 수 있습니다.** 그러나 4차 **최종 제품 인수**는 승인된 자료 DB→API→화면 연계, 정정/취소/권한/롤백·원본 시뮬레이터 회귀를 실제 운영 환경에서 확인한 뒤에만 선언합니다.

### 7.1.1 학사자료 데이터 경계·수명주기 정책 (확정)

**보존은 데이터 유형·사용 목적별로 다르게 하며, 모든 원문과 과거 시간표를 DB에 영구 축적하지 않습니다.** 2010학년도 이후 전체 전공은 서비스 대상 범위이지 모든 시점·자료가 이미 수집되었다는 주장이 아닙니다. 자료 이용권한·독립 검수가 확보된 관측부터 저장하고 누락은 UNKNOWN으로 유지합니다. 아래 기한은 **팀의 초기 보존 목표**이며 학교가 허가한 이용조건·별도 보존 의무가 우선합니다.

| 보존 분류 | 상세 데이터의 경계 | 오래 남길 검증 정보 |
|---|---|---|
| 현재 강좌·분반 | 현재/예정 학기 + **최근 3개 학년도**(당해 및 앞선 2개; 계절학기 포함)의 시간·요일·강의실·담당교수 표시 | 과목 기본정보·정정·현재 유효한 강의 상세 |
| 과거 개설 관측 | 허가·검수된 **2010년 이후 학기 전체**, 오래된 상세 분반은 정리 | 과목 ID×학기×캠퍼스별 OFFERED/NOT_OFFERED/UNKNOWN, **관측된 분반 수**, 완전성·출처 판본·최초 확인 시각 |
| 단순·일회성 공지 | 학생에게는 유효한 **최신 승인판**만 제공; 종료/정정/취소 후 **90일** 상세 확인 | 검수·철회·분쟁에 필요한 최소 공지 ID·해시·시각(권리상 허용될 때만) |
| 반복 학사행사 | 과거 공지 장문은 정리; 공식으로 확인된 개최 회차의 구조화 정보는 장기 보존 | 연도·캠퍼스·시작/종료·**학생 마감**·정정/취소·대상·근거; 예측값은 실제 개최 기록으로 승격 금지 |
| 학칙·졸업요건·교과과정 | **2010학년도 이후 대상 학생에게 현재 또는 향후 적용될 수 있는 모든 승인 판본**, 소급·예외·대체관계 | campus/cohort/program/track/validFrom/To, 조항·정정 관계·출처/승인 |

| 출처·검수·승인·철회·감사 | 자료의 합법적 이용/재검증/복구에 필요한 최소 메타데이터 | 출처 URL·판본 SHA-256·확인/승인/철회 시각, 참조 관계; 원문 전체/학생 개인 원장은 보관 금지 |

**분류 우선순위:** 하나의 공지가 중복 성격이면 **학칙·자격 변경 > 반복 학사행사 > 일반·일회성** 순으로 판단하고, 원문은 단순 공지의 짧은 수명에 따라 정리하더라도 추출된 규정·확정 행사 이력과 필요한 증빙은 지우지 않습니다. 90일은 **확인된 마지막 종료·대체·취소일**부터 계산하고 종료일·분류가 불명확하면 자동 정리하지 않고 검수 보류합니다. 단순 게시일을 학생 마감/종료일로 추정하지 않습니다.

**상세→역사 전환:** 최근 3개 학년도 밖으로 밀린 분반은 검수된 과목×학기×캠퍼스 관측과 분반 수를 먼저 확정하고, 이후 담당 관계·분반 상세를 순서대로 정리합니다. 외래키로 연결된 이력·검수 근거를 깨지 않으며, 과거 미관측을 NOT_OFFERED로 바꾸지 않습니다. 예측과 rolling-origin 평가는 **해당 예측 시점에 이미 관측·승인된 데이터**만 사용합니다.

**공개용 자료:** Supabase는 목적별 정규화 원장과 원천 근거를 관리하고, 학생에게는 현재 승인된 공지·FAQ·최근 강좌 및 **요청한 과목/행사에 필요한 역사 집계**만 공개합니다. 통째로 중복 저장한 JSONB 스냅샷을 무기한 누적하거나 학교 전 학기 원장을 매 페이지 조회마다 전송하지 않습니다. 검수된 현행 공개판 1개와 권리·기한이 유효한 제한된 롤백 후보만 payload를 유지하는 것을 목표로 하며, 나머지는 필요한 manifest/해시·감사 기록으로 축소하는 **별도 마이그레이션/수집·API 구현**이 필요합니다. **현재 Draft #93 SQL에는 기간 만료 자동 정리·압축·payload 중복 제거/부분 조회가 구현되어 있지 않습니다.** 이를 시행했다고 표시하거나 운영자 승인 없이 자료를 DELETE하지 않습니다.

**정리·권리 게이트:** 철회/불허 시에는 공개부터 즉시 차단하며 안전하지 않은 이전판으로 되돌리지 않습니다. 물리 삭제·분반 집계·스냅샷 축약은 출처별 권리 확인, 누락·관계 영향 미리보기, 독립 검수·승인, 운영자의 백업/복구 확인, 전후 DB 용량 실측, 작성자 외 협업자 코드 리뷰 이후에만 수행합니다. 운영 단계별 체크리스트는 [학사자료 수명주기 운영 지침](academic-data-lifecycle-operations.md)이며, 정책의 기준은 **이 아키텍처 §7.1.1**입니다. 구현/실측 추적은 [#64](https://github.com/ot4562-glitch/Hanmo_develop/issues/64)·[#65](https://github.com/ot4562-glitch/Hanmo_develop/issues/65)·[#66](https://github.com/ot4562-glitch/Hanmo_develop/issues/66)·[#67](https://github.com/ot4562-glitch/Hanmo_develop/issues/67)입니다.

### 7.2 데이터 갱신 아키텍처

```text
공식 공개 학사자료 또는 허가된 API
  → 정기 수집(GitHub Actions / 승인된 워커)
  → 원문 식별자·수정일·해시로 변경 감지
  → JSON/CSV 핵심 필드 정규화·중복 제거·자료별 수명주기 분류
  → 규정·학생 마감·행사 관측/완전성·정정/취소 검증
  → 독립 검수·승인 → 현행 상세 또는 역사 관측/규정 판본으로 분리 반영
  → 공개 읽기 전용 API → 학업 플랫폼
```

학교가 공식 API 또는 자동 수집 권한을 제공하지 않는 경우 **실시간 자동 갱신을 보장하지 않습니다**. 오류·누락·취소·정정에 대비해 확인 시각, 보류 표시, 재시도와 **정적 JSON 대체 경로**를 둡니다.

허용된 출처만 정해진 주기로 확인하며 재시도 후에도 실패하면 운영자가 처리합니다. 학생은 로그인 없이 **승인된 공통 학사자료만** 읽습니다. 수집·검수·승인 쓰기 권한을 분리하고 관리 키는 운영 환경에만 둡니다. 지연·장애 시 마지막으로 검수한 자료가 여전히 유효하면 확인 날짜와 함께 제공하고, 유효한 자료가 없으면 ‘확인 필요’와 확인 가능한 원문을 안내합니다. 개인 캠퍼스·전공 선택, 이수 원장, 성적, 수강계획과 체크 상태는 브라우저에 보관합니다. 학교 계정·인증 정보 및 학생의 원본 입력을 공통 자료 DB에 전송하는 경로는 두지 않습니다. 개인 동기화는 이 범위에서 제외하며 로컬 백업·내보내기·삭제는 §4.8을 따릅니다. - **실연동 인수 기준:** DB/API의 판본·원문 검수·읽기 권한·보안·정적 대체 경로·정정/취소·운영 실패 복구·브라우저 E2E를 실제 승인된 환경에서 확인하고 인수합니다. 문서 인계만으로 제품 완성이나 4차 최종 인수를 선언하지 않습니다.

### 7.4 학교 회신 전 확정할 데이터·배포 경계 (#30·#31·#32)

**설계 대안과 선택:** (A) 1차부터 브라우저가 임의의 원문·Supabase 내부 테이블을 조회하는 방식은 권리 불명 자료 노출, 검수 우회, 판본 불일치 위험으로 채택하지 않습니다. (B) **1차는 검수된 불변 정적 스냅샷만 조회하고, 3차는 같은 스냅샷 계약을 Supabase의 승인된 공개 읽기 경로로 제공**하는 방식을 채택합니다. 실제 자동 수집·DB 계정·실환경 연결은 허가와 관리자 합의가 이루어진 뒤 시작합니다.

**논리 ID와 검수된 공개 릴리스 계약:**

| 구성 | 키/관계(설계) | 무결성·버전 조건 |
|---|---|---|
| 출처·사용권 | `sourceId`, 관할·원문 URL·권리 범위·확인일 | 사용권 상태 `UNKNOWN/ALLOWED/LIMITED/DENIED/REVOKED`; 권리 미확정 상태로 자동 수집·원문 재배포 금지 |
| 강의·개설/분반 | `courseId`, `termId`, `campus`, `offeringId`, `sectionId`, `sourceRevisionId` | 동일 과목·학기 중복 및 빈 관측 구분; 완전성이 입증되지 않으면 미개설 확정 금지 |
| 공지·이벤트 | `noticeId`, `revisionId`, `eventOccurrenceId`, `sourceId` | 게시·시작·학생 마감·행정 마감·정정/취소 분리; 수정하면 새 불변 판본을 생성 |
| 학칙·요건 | `rulePackId`, `requirementId`, `semanticKey`, `validFrom/To` | 캠퍼스·입학년도·전공/트랙·시행일이 충돌하면 선택 보류 |
| 검수·승인 | `sourceRevisionId`, `contentSha256`, `reviewerId`, `approverId` | **동일인 검수·승인 불가**, `APPROVED` 자체 문자열은 권한 증거 아님; 철회/권리변경 이력을 분리 |
| 정적·API 스냅샷 | `snapshotId`, `manifestSha256`, `publishedAt`, `revokedAt`, `schemaVersion`, `faqIndexRevision` | 공지·개설·FAQ가 **동일한 승인 스냅샷**을 가리켜야 공개; 불변 발행 뒤 포인터만 교체 |

실제 SQL에서는 외래키·유니크/중복방지 키, `sourceId+sourceRevisionId`, `snapshotId+documentId`, `campus+termId+courseId` 조회 인덱스, 게시/적용 시간 범위를 점검합니다. **업데이트는 기존 검수 판본 덮어쓰기보다 새 불변 판본 + 활성 포인터 교체**를 우선합니다. 중단/롤백은 승인된 직전 유효 스냅샷으로만 가능하며 **권리 철회·취소·중대한 정정**이 있는 구판을 자동 되살리지 않습니다. 물리 SQL/권한·인덱스 실행계획과 용량 수치는 [#64](https://github.com/ot4562-glitch/Hanmo_develop/issues/64)에서 실제 환경이 허가된 뒤 확정합니다.

**수집/갱신 상태 머신:** `PERMISSION_CHECK → FETCH(승인 출처만) → NORMALIZE → QUARANTINE → REVIEW → INDEPENDENT_APPROVAL → PUBLISH → MONITOR`. 실패/충돌/중복/권리 불명은 `QUARANTINE`으로 되돌리고, 취소·철회는 `REVOKED`로 공개 연결을 무효화합니다. 학교가 정기 접근을 허용하기 전에는 `FETCH`를 실행하지 않습니다. 허용된 뒤에도 출처별 최소 필요 주기·조건부 요청·지수 백오프·상한 재시도·수동 실패 큐를 사용하며 **실제 호출 주기와 쿼터는 허가 회신 및 계측 후** 정합니다. API 장애의 대체는 `schemaVersion`, `snapshotId`, 권리/유효성·최종 검수 시각이 확인되는 정적 파일만 허용합니다. 안전한 대체가 없으면 ‘자료 확인 필요’로 표시합니다.

**공개 읽기/API 및 RLS:** 학생에게는 별도 로그인이 없는 **승인·비철회 공통 학사 데이터 읽기**만 제공하며 관리자 테이블·원장·검수 원문·학생 성적은 Data API에 노출하지 않습니다. 공개 스키마에 테이블을 두는 경우 **RLS 활성화 + 최소 `GRANT` + 공개 데이터에 한정된 `SELECT` 정책**을 모두 확인합니다. 공개 뷰는 무조건 RLS가 적용된다고 믿지 않고 PostgreSQL 버전에 맞춰 `security_invoker` 또는 비공개 스키마/명시 권한 구성을 검증합니다. API 키는 공개 브라우저용 **publishable key**와 서버 비밀키를 구분하고 `service_role`/secret 수집키를 HTML/JS/GitHub Pages/정적 ZIP에 넣지 않습니다. `SECURITY DEFINER`를 간단한 권한 우회책으로 도입하지 않습니다. `anon` 쓰기·검수/승인·취소 API는 기본 거부하며 브라우저의 출처 문자열 또는 클라이언트 JWT 사용자 메타데이터를 검수 권한 증거로 사용하지 않습니다. [Supabase RLS 공식 지침](https://supabase.com/docs/guides/database/postgres/row-level-security) · [API 키 안내](https://supabase.com/docs/guides/getting-started/api-keys)

**개인정보/비용 경계:** 캠퍼스·전공 선택, 개인 이수/계획/체크 내역은 로컬 기본값으로 유지합니다. 서버에는 공통 공개 스냅샷 조회만 허용하며 개인 원본 업로드·선택형 동기화·학교 로그인 인증은 3차 기본 기능이 아닙니다. **월 지출 목표/상한은 $0(Supabase Free만 사용)으로 확정**하되, DB/인덱스·전송량·성장률의 실측 전에는 학교 전체 자료 수용량이나 처리 가능 사용자 수를 약속하지 않습니다. 무료 제한에 근접하면 유료 업그레이드 대신 자동 추가 수집을 중단하고 저장량·조회량 최적화 및 검수된 정적 스냅샷 대체를 사용합니다.
