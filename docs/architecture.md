# Hanmo Develop — 아키텍처

> 현재 유효한 제품 및 기술 설계입니다. 실제로 구현된 기능과 앞으로 구현할 목표를 구별합니다.  
> **이 문서는 변경 이력이나 회의록이 아닙니다.** 설계가 바뀌면 이전 안을 남기지 않고 현재 안으로 수정합니다.

## 1. 프로젝트 목표

한모를 **수강신청할 때만 방문하는 모의연습 사이트**에서 **입학 후 수강계획부터 졸업까지 지속적으로 이용하는 비공식 학업 플랫폼**으로 확장합니다.

- **포함:** 학기별 강의·분반·담당교수, 시간표·대체과목, 학점·재수강·이수요건, 주전공·이중전공·부전공, 수강신청·전공신청·학사공지·학사일정, 졸업시험·논문·인증·졸업사정, 학적·학점교류, 학칙 개정 영향, 강의 개설·학사행사 전망, 근거형 학사 FAQ, 학업 상담 경로, 교환학생·국제학생 학업 준비.
- **제외:** 고용·취업·진로·채용·직무 멘토·NCS, 실제 학교 수강신청 자동화, 학교 계정 인증 대행, 공식 졸업사정의 대체.
- **일관성:** 기존 BASIC / TIME / SELECT 모의신청의 화면·조작 충실도를 지킵니다. 학생에게는 **현재 부족한 것, 근거, 다음에 할 일, 불확실성**을 함께 제시하며, 학사 판단은 검증된 규정과 적용 대상이 확인되는 범위에서만 안내합니다. 계산 가능·소스 이식·화면 작동·공식 검증·출시 적합은 별도 상태입니다.
- **현재 UI와 기능 우선순위:** `학점 정리`는 사용성을 재검토하는 선택 기능입니다. 수강신청 원장과 검수된 시간표가 필요한 **실제 대체과목 검색·추천 및 분반 시간 충돌 기능은 현행 2차에서 제외하고 후속 보류**합니다. 포크의 **합성 대체과목 검색·번호 충돌 데모 및 관련 미사용 실험 코드는 제거**하며, `LAST_VALID`의 가상 실패 알림과 `RECONNECT`의 가상 404·복귀만 별도 기본 OFF 설정으로 유지합니다(§5·§10.1). 이 범위 변경은 원본 BASIC/TIME/SELECT와 실제 학교 시스템에 영향을 주지 않습니다.

**연결된 사용 흐름:** ② 과거 개설 관측 → 다음 학기 수강계획과 대안 작성 → ③ 예상 학사행사 구간에서 준비할 일 확인 → ① 가상 실패·재접속 훈련으로 계획을 점검합니다. 학사공지 **예측**은 공식 공지가 발표되기 전의 대비 수단이며, 공식 정정·취소/확정 공지가 있으면 항상 이를 우선합니다.

**구현 자산과 대외 주장:** ②·③은 앞서 HUFS One AI 학업 모듈에서 개발된 개설·행사 전망 접근법을 **선별 검토·재사용할 수 있는 후보**입니다. 한모에 검증된 과거 전수 자료, 출시 가능한 UI, 공식 데이터 승인 및 소스 재배포 권리가 모두 확보되었다는 의미는 아닙니다. 현재 조사만으로 “국내 최초”, “유일”, “학교·비공식 어디에도 없는 기능”을 객관적으로 확정할 수 없으므로, 외부 홍보에서는 구체적 기능 차별화를 설명하고 절대적 독점 표현은 별도 비교 검증 후에만 사용합니다. ### 1.2 첫 학생용 출시 범위

대외적으로 설명할 핵심 목적은 **“내 전공 공지를 찾고, 다음 학기 수강신청을 미리 준비하는 곳.”**입니다. 현재 홈페이지는 기존 한모의 공지·시간·모의신청 버튼을 유지하므로 이 문구를 홈의 별도 대형 안내 블록으로 렌더링하지 않습니다. 학생이 개설 근거를 찾고, 예상 준비 기간과 학교가 확정한 마감을 구분하고, 연습에서 실패 뒤 알맞게 대처하는지를 검증합니다. 유사 서비스 비교는 기능·출처·확인일을 기록해 [#38](https://github.com/ot4562-glitch/Hanmo_develop/issues/38)에서 완료합니다.

**필수 사용자 흐름은 캠퍼스·전공 선택 → 중요공지와 적용 근거 확인 → 개설 이력으로 다음 학기 준비**입니다. 첫 적용 대상은 서울·글로벌캠퍼스의 2010학년도 입학생부터 모든 전공입니다. 설계 목표상 입학년도는 적용 조건 확인에 활용하며, **현행 `내정보` 저장 화면은 입학년도를 필수 입력받아 `YYYY학번`으로 표시**합니다. 실제 학교 학번 전체나 로그인 정보는 수집하지 않습니다. 학교 계정, 성적표, 이수 원장 없이 이 흐름을 완료할 수 있어야 합니다.

1차의 기술 우선순위는 **검수된 공지·개설 이력 스냅샷과 한국어 근거 FAQ**입니다. 먼저 동일한 검수 스냅샷으로 필수 흐름을 브라우저에서 검증합니다. FAQ는 해당 스냅샷으로 §4.6의 평가를 통과한 범위부터 연결합니다. 반복 학사행사 예상 구간은 과거 자료가 검증된 행사 유형부터 제공하고, 개인별 졸업 위험 진단·전공 변경 시뮬레이션은 로컬 이수 기록 입력과 판본별 RulePack 검증 후 확장합니다.

### 3.1 실행 경계

- **정적 우선:** 1차에서 React 의존 화면은 **정적 HTML과 DOM 이벤트**로 재구성하고, **TypeScript를 유지보수 원본 소스**로 사용합니다. TypeScript 계산 로직은 파일·로컬 저장소·추후 API와 분리하며 배포 때 일반 JavaScript로 빌드합니다. 1·2차는 인터넷이나 인증 서비스가 없어도 사용자 자료와 번들 예제로 작동해야 합니다.
- **2차 언어 경계:** 기존 시뮬레이터의 시나리오는 **JavaScript·기존 HTML/CSS로 직접 구현**합니다. React나 TypeScript 개발환경을 기존 페이지의 필수 의존성으로 도입하지 않습니다. 1차 코어와 연동이 필요하면 빌드된 JavaScript 공개 어댑터 및 명시적 입력/출력 계약을 사용하며, 원본 TypeScript나 학생 이수 원장을 시뮬레이터에 결합하지 않습니다.
- **3·4차 전환 경계:** 3차 Supabase 데이터 어댑터·연동을 진행하는 동안 1차 TypeScript와 2차 JavaScript를 병행 유지합니다. 4차에만 1차 유지보수 소스를 **JavaScript + JSDoc 및 `checkJs` 등 정적 검사**로 옮기고 원래 계산 결과·API 계약을 보존합니다. 생성된 JavaScript 번들을 수동 편집하지 않습니다. Supabase SQL·RLS·운영 도구는 기술상 필요한 언어를 유지합니다.
- **단일 진실의 출처:** 공식 확인을 주장하는 자료는 운영 검수된 릴리스 자산과 그 판본·해시에서만 채택합니다. 형식 검증에 통과한 사용자 파일은 비공식 자료입니다. 학교 자료를 자동 갱신하지 못하는 경우 마지막 검수시각을 표시합니다.
- **학생 정보:** 현재 `html/planner.html`(`내정보`)에서는 캠퍼스·주전공·입학년도(화면 표시는 `YYYY학번`)가 필수이고 이중전공 또는 부전공은 선택 입력입니다. `js/student-preferences.js`가 로컬 브라우저에 저장하고 `js/student-profile-bar.js`가 상단 우측 요약을 구성합니다. 이 값은 **사용자가 적은 정보**이며 학교 계정 로그인·학적 확인·고유 학번 인증이 아닙니다. 개별 성적/이수/학적 파일은 사용자가 로컬에서 불러와 관리하며 원격 전송·공개 Git 기록·서버 기본 동기화가 없습니다. 브라우저 데이터 삭제·내보내기·공유 PC 주의를 제공합니다.
- **재사용 자산:** `js/academic/`에는 선별한 브라우저용 학업 계산 코어·테스트만 둡니다. 예전 원본 235개가 포함된 `legacy-academic/` 보존 트리와 React·Fastify·PostgreSQL·비학업 원본은 **현재 PR #1~#5의 새 커밋 계보와 배포 번들에서 제외**했습니다. 필요 참조는 소스 원저작자·권리 범위를 확인한 별도 자료에서만 하며 포크에 다시 무더기 복사하지 않습니다.
- **원본 보존·제한적 변경 조건:** 승인된 범위에서 `index.html`·`html/vsugang.html` 및 공통 CSS/JS를 이미 수정한 상태입니다. **`html/practice.html`·`html/selectZone.html`과 기존 JS/CSS는 원본 동작 비교 기준선**입니다. 원개발자의 사용자 전달 답변에 따라 `selectZone`의 필요한 변경 자체는 허용할 수 있으나, 실제 수정은 별도 코드 PR·원본 대비 회귀·배포 승인을 거쳐야 합니다. 특히 **SELECT 버튼을 눌렀을 때 기존 대기 번호 창이 정상 표시되는지**와 **Enter 연타 시 기존처럼 ‘수강신청하시겠습니까?’ 확인 안내가 반복 표시되는지**를 실기기에서 확인합니다(§5.3). 실제 운영 CNAME·도메인은 임의 반영하지 않습니다.
- **소스 선별:** 기존 이식 과정에서 필요한 학업 화면·계산 코어·테스트만 남기고 `degree-rescue/`는 해체해 현재 `html/`·`js/academic/`·`css/`·`docs/` 등으로 재배치했습니다. 과거 PR #1~#5는 현재 미병합 UI의 기준이 아닙니다. 옛 참조 파일·권리 미확인 코드·개인정보 샘플은 공개 묶음에서 제외합니다. **동결의 의미:** 현재 배포된 사용자 화면의 **임의 재디자인·내비게이션 재편·추가 독립 페이지 생성은 하지 않습니다**. 보안/접근성/치명적 버그·권리 문제를 수정해야 한다면 사용자 승인 범위를 분명히 하고 **작은 수정 → 기존 화면 비교 → 전체 회귀 → 배포/복구 확인** 절차를 적용합니다. 학업 데이터·알고리즘 개발은 진행할 수 있어도 UI가 달라지는 기능 추가는 별도로 결정합니다. 동결은 현재 UI의 완전한 Windows 접근성·실기기 검증이 끝났다는 주장과 다릅니다.

**검증·복원:** `npm run check:legacy`, `npm run check`, `npm run smoke`, 합성 돌발상황·홈 뷰포트/상단 메뉴·내정보 보존 테스트, `dist/`의 정적 자산/PC-only 검사, Windows Chrome/Edge에서 1280×720·1920×1080 및 고배율/키보드 확인을 사용합니다. 문제가 생기면 **기준선의 UI 관련 파일만** 복원하고 이미 검증된 다른 코어·자료 변경을 통째로 되돌리지 않습니다. 문서만 수정할 때는 현재 UI와 원본 코드 SHA·테스트 계약이 그대로인지 확인합니다.

## 4. 1차 — 입학 후부터 졸업까지의 학생용 학업 플랫폼

새 학업 화면은 루트의 `html/`에 구축합니다. 기존 모의신청 화면을 보호하며 TypeScript 코어와 계약은 `js/academic/`, 공개 스타일은 `css/`, 스냅샷은 `data/`, 검증 스크립트는 `scripts/`에 둡니다. 코어는 공식 규정·출처가 검증되지 않으면 사용자 입력에 대한 **조건부 결과/확인 필요**만 반환하며, 학교의 신청·성적·졸업 확정 기능을 대행하지 않습니다. 아래 항목은 **채택한 목표 기능과 계산 계약**이고, 실제 학생 화면/정본 데이터 구축 여부는 별도로 검증합니다.

### 4.1 학생 프로필·이수 원장·졸업 계산

- **적용 조건:** 서울/글로벌 캠퍼스, 입학년도, 입학전형·교육과정 버전, 주전공·이중전공/부전공·전공심화 선택, 학적/등록학기, 목표 졸업학기를 명시합니다. 필수 축이 없거나 전공 변경 이력이 불명확하면 정확한 RulePack을 임의 선택하지 않습니다.
- **학점 상태 분리:** `EARNED`(취득 완료), `IN_PROGRESS`(수강 중), `PLANNED`(계획), `PENDING`(인정 미확정), 공식 제외/재수강 무효화를 분리합니다. `1 credit unit = 0.5학점`의 정수 단위를 사용하고 과목 동일성·중복·재수강 승인·취득 학기 종료 시점을 검증합니다. 수강 중/계획 학점을 이미 취득한 학점으로 합산하지 않습니다.
- **요건 범위:** 총학점, 교양필수/영역, 전공필수·선택, 필수·동일/대체 교과목, 선택묶음, 영역 분포, 학점교류·교환·편입 인정, 재수강/학점포기, 등록학기, 평점 요건의 확인 가능성, 졸업시험/FLEX·논문·언어 인증·서류·졸업사정의 비학점 조건을 각기 분리합니다.
- **결과 계약:** 요건별 `SATISFIED / UNSATISFIED / NEEDS_REVIEW / NOT_CHECKED / NOT_APPLICABLE`과 근거 조항·계산 판본·남은 학점 또는 확인할 사유를 제공합니다. 전체 요약 `READY`는 **검증한 입력에 대한 계산 상태**이지 '졸업 승인'이 아닙니다. 출처가 모자라면 `INSUFFICIENT_DATA`, 규칙·이수 여부가 충돌하면 `NEEDS_REVIEW`로 보류합니다.
- **전공 변경 What-if:** 주전공 변경, 이중전공 신청/변경/포기, 부전공 전환, 전공심화 경로에 따른 전후 부족 요건과 수강 계획을 비교합니다. 변경은 가정일 뿐 실제 전공 배정, 지원 자격, 합격이나 학칙 적용 변경을 단정하지 않습니다.
- **장기 경로:** 남은 요건, 학기별 최대학점, 과목 선후수, 같은 학기 실제 개설 가능성, 대체 과목과 학적 변경을 고려해 2~4학기 계획 A/B/C와 졸업 지연 위험을 비교합니다. **현재 한 학기 제약 검사 코어와 구별되는 신규 최적화 기능**이며 공식 강의·교과과정 정본 없이는 조건부 시나리오로만 표시합니다.

### 4.2 학칙 원문 승인·판본 관리·학생별 개정 영향

- **첫 적용 대상과 검수:** **서울·글로벌캠퍼스, 2010학년도 입학생부터, 모든 전공**을 1차 대상 범위로 정합니다. 캠퍼스·입학년도·전공별로 학점·전공필수·졸업시험·논문 등 요건의 정본·시행일·경과 규정을 대조합니다. 개인 졸업 진단은 독립 검수·승인을 마친 조합부터 제공합니다. 대상 범위 안의 미확보·미검수 조합도 ‘확인 필요’로 표시하고 다른 입학년도·전공의 요건을 대신 적용하지 않습니다. [#11](https://github.com/ot4562-glitch/Hanmo_develop/issues/11)
- **RulePack 키:** 캠퍼스·학번 범위·주/이중/부전공·입학전형·교육과정/트랙·적용 시작/종료·규정 버전. 같은 조건에서 승인된 규정이 둘 이상 충돌하거나 예외의 적용 범위가 확정되지 않으면 자동 선택을 중단합니다.
- **원문 재현성:** 학칙 조항·단서·예외·각주를 빠짐없이 독립 목록으로 만들고 `sourceSpanRef`, 원문 URL·해시, 조항 ↔ `requirementId` 양방향 연결과 숫자 일치 여부를 확인합니다. 원문 목록 자체를 후보 RulePack과 동일한 도구가 생성했다면 독립 검수가 아닙니다.
- **승인 게이트:** 검수자와 승인자를 서로 다른 역할로 두고 적용 시점·공개 시점·검토 시각·원문 판본·범위·개정 승계 관계를 확인합니다. `APPROVED` 문자열이나 사람 이름을 사용자 JSON에 넣었다고 실제 승인이 되지 않습니다. 문제가 있으면 기존 검증 판본을 유지하거나 '확인 필요'로 처리합니다.
- **개정 비교:** `rule-approval.ts` 및 `rule-diff.ts`의 개념을 채택합니다. 안정적인 `semanticKey`/요건 ID를 전제로 같은 학생 이수 원장을 개정 전·후 RulePack에 적용해 `ADDED / REMOVED / CHANGED / UNCHANGED`와 `GAINED / LOST / SAME / UNKNOWN`을 구분합니다.
- **변경 영향 화면:** 학생에게 '새 필수과목', '충족 → 미충족 가능', '면제/대체 인정 변경', '추가 확인/이수 필요', '적용 대상 아님/불명'을 근거 조항과 함께 설명합니다. 학사 적용일·학번 소급 규정은 임의 해석하지 않습니다. 과목의 영역 재분류가 바뀌었다면 새로운 분류 원장(`nextAttempts`)이 없는 경우 결과를 확정하지 않습니다.
- **판본 역행 방지:** 이전 규정의 충족 결과를 새로운 규정으로 그대로 복사하지 않습니다. 개정 체인 단절·중복/겹침·승인되지 않은 규정·규정 ID 변경을 발견하면 차이표를 보류하고 학생에게 확인할 원문을 제공합니다.

### 4.3 강의·교수 표시·시간표·계획 스냅샷

- **검색:** 학수번호·과목명·학기·캠퍼스·분반·학점·개설학과·요일/시간·강의실·담당교수 **표시명**. 과목 고유 식별자, 분반/개설 학기, 수업 담당 이력을 분리합니다. WIS 수동 저장 HTML/CSV의 형식·중복·학기·범위·출처를 검증합니다.
- **강의 검색의 순위·안전:** 검증된 학수번호·분반·학기 **정확 일치 우선** → 과목명/교수 표시명 필드 검색 → 오타·띄어쓰기·약칭 후보 순으로 연결합니다. 캠퍼스·개설학기 및 동일·대체과목 관계가 미검수이면 관련성이 높아도 공식 개설·동일과목으로 단정하지 않습니다. #53·#40 공통 검색 품질 계약을 적용하지만, 현재 가상 검색 결과를 실강좌로 승격하지 않습니다.
- **자료 사실성:** 로컬 WIS 저장본에 나오는 교수 이름은 해당 수업의 표시명이지 재직·인사·지도교수·연락처/강의평가 정본이 아닙니다. 사용자 제공 CSV는 형식 검사를 통과해도 `UNVERIFIED`입니다. 과목 코드에서 분반을 자동 분리하거나 제목만으로 동일 교과목이라고 추정하지 않습니다.
- **로컬 파일 계약:** 저장한 WIS HTML과 정해진 형태의 CSV를 받고, 학기·캠퍼스·코드·빈 값·중복을 검증합니다. 기존 8개 컬럼(`courseCode, courseName, credits, category, major, semester, campus, cohort`)과 원래 강좌 코드를 유지해 검증된 행만 UTF-8 CSV로 내보냅니다. 교수 이름·인원·개인정보는 제외합니다. CSV 가져오기 화면과 입력 오류 시험은 [#43](https://github.com/ot4562-glitch/Hanmo_develop/issues/43)에서 검증합니다.
- **수강계획 검증:** 한 학기 학점 상한, 선수요건, 시간표 충돌, 인정 영역, 이미 들은 과목, 분반 개설 상태를 함께 검사합니다. 확인된 분반이 없으면 강의·시간을 가상 생성하지 않고 `확인 필요`로 남깁니다. 대체 과목은 공식 동등성·학칙 범위가 확인되어야 '인정 가능'이라고 표기합니다.
- **계산 스냅샷:** 학칙 `rulePackVersion`, 이수 원장 `ledgerVersion`/`transcriptVersion`, 강의·분반 `catalogVersion`, 사용자 계획 `planVersion`, 행사·공지 자료 `noticeSnapshotVersion`, `asOf`, 적용 조건 및 출처 목록을 결과마다 결합합니다. 판본·시간표·폐강·정정·규정 승인/철회 중 하나라도 바뀌면 이전 결과는 `STALE / 재계산 필요`가 되며 저장된 추천을 재사용하지 않습니다.
- **재현성:** 동일 스냅샷과 동일 입력은 동일 결과를 내야 합니다. 단순 파일명/문자열 버전이나 로컬 체크 상태는 공식 소스의 최신성/승인을 증명하지 않습니다. 버전 하나가 누락되면 그 자료를 참조한 결과만 안전하게 보류하고 잘못된 부분 갱신을 막습니다.

### 4.4 학사공지·신청기간·미충족 요건에서 행동까지

**학생 → 규정·이수 원장 → 미충족/확인 요건 → 필요한 과목·신청·제출 → 적용 공지·실제 마감 → 담당 부서/원문 확인**을 하나의 사용자 흐름으로 연결합니다.

| 영역 | 공지 및 행동 | 연결할 학생 조건 |
|---|---|---|
| 수강 | 사전신청, 본신청·정정·철회, 계절학기, 개설·폐강 | 부족 과목·분반·학점 상한·선수 요건 |
| 전공 | 주전공/세부전공, 이중전공 신청·변경·포기, 부전공·전공심화 | 학번·학적·전공 조합·지원 조건 |
| 졸업 | 졸업시험/FLEX, 논문, 외국어 인증, 사정·제출 서류·수료·학위 | 비학점/학점 요건·목표 졸업학기 |
| 성적·학적 | 성적 정정·재수강·학점포기·학점교류 인정, 휴·복학·등록 | 원장 인정 상태·학적·등록학기 |
| 국제·지원 | 교환학생 지원·학점 인정, 학사 FAQ, 교직/학업 상담 | 언어·이수학기·캠퍼스·관련 교육과정 |

- **공지 출처 계약:** 공지 ID/개정 ID, 게시/정정/취소 시각, 작성 부서, 원문 URL, 학생 적용 범위, 학생 접수 마감 `studentDeadline`, 행정 보고 마감 `adminDeadline`, 시험/행사일, 공지 유형·학기, 근거 요건 `requirementRefs`·과목 `courseRefs`를 구분합니다. 게시일은 접수 마감일이 아니고 행정 마감은 학생 D-day가 아닙니다. 모든 날짜는 `Asia/Seoul`로 표시·계산합니다.
- **학생 대상 판정:** 캠퍼스·학번·전공 역할·학적·졸업 목표·요건별 상태 중 필요한 값이 없으면 `UNKNOWN`; 명확히 불일치하면 `NO`; 충분히 확인되면 `YES`. 자기 입력 졸업 목표만으로 공식 졸업예정자 신분을 추정하지 않습니다.
- **요건 자동 연결:** `openRequirementIdsFromAudit`와 공지 `requirementRefs`를 연결하되 **동일한 검증 RulePack의 요건 ID**여야 합니다. 학생이 직접 적거나 정적 계산에서 도출한 '미충족 후보'는 공지를 찾아주는 힌트일 뿐 '공식 충족/비대상'을 판정하지 못합니다. 후보가 없다는 이유로 필수 공지나 검토 필요 공지를 숨기지 않습니다.
- **공지 정정/취소:** 동일 ID 판본 충돌·미래 게시·철회/취소·권리 회수·출처 불명은 격리하고 과거의 확인된 공지를 무조건 되살리지 않습니다. 동일 제목 여러 개를 하나의 확정 마감으로 합치지 않습니다.
- **중요도 모델:** 검수되고 적용 대상이 `YES`인 필수 공지 중 **학생 마감 7일 이내**를 최우선(`CRITICAL_DUE`), 그다음 학업 필수(`ACADEMIC_REQUIRED`), 학생 관심/직접 관련(`PERSONAL`), 일반(`GENERAL`)로 분류합니다. 미검수 후보는 검토 목록으로 분리하며 확인된 필수 공지로 격상하지 않습니다. 지난 마감은 '기한 경과·담당부서 확인'으로 표시하고 상단 고정 대상에서 제외합니다.
- **검색 주제 분류 ≠ 학생 대상 확정:** 검색어가 전공·졸업·학점 관련 단어와 유사하더라도 그 사실만으로 학생 적용 대상 `YES`나 `CRITICAL_DUE`를 판정하지 않습니다. 검색 주제 분류 혼동/오탐은 #40, 근거 있는 공지 적용·마감 분류는 #51의 별도 검증 게이트로 둡니다.
- **상단 고정/캘린더:** 검수된 공지 중 학생에게 해당하고, 정확한 학생 마감이 남아 있으며 **7일 이내**인 필수 공지를 중요도·마감순으로 **최대 2건** 고정합니다. 적용 여부와 자료 검수 상태는 별도 값으로 관리합니다. 대상이 불명확하거나 자료가 미검수인 공지는 '원문 확인 필요' 목록에 노출하고 원문 링크를 제공합니다. 달력은 '개최일/시험일', '학생 신청 마감', '사용자 개인 목표' 표식을 구분합니다. ### 4.5 강의 개설 전망 및 반복 학사행사 예상 구간

**학생 경험의 목표:** 공식 개설 발표 전에 과거 같은 시즌의 개설 패턴으로 수강계획과 대체안을 미리 작성하고, 졸업시험·이중전공 신청/변경 등 반복 행사의 **준비 예상 구간**을 개인 학업 달력에 참고 표시합니다. **예측은 실제 개설 보장이나 학교 확정 신청 시작·마감 알림이 아닙니다.** 확인 가능한 과거 관측·원문 링크·표본·신뢰 수준을 함께 설명합니다.

- **강의 개설:** 같은 시즌의 과거 개설·미개설을 관측값으로 사용하고 공식 확정 공지·개설 목록은 가장 높은 우선순위로 별도 표시합니다. 누락된 학기를 미개설로 채우지 않으며 관측 범위/완전성을 표기합니다. `k/n`을 곧바로 미래 확률 `k/n × 100%`로 표시하지 않습니다. 가정 변경·rolling-origin 백테스트를 통과하지 않은 확률 보정은 보류합니다.
- **관측 원장:** 출처·판본·캠퍼스·학기·수집 범위별로 `개설 확인`, `미개설 확인`, `미관측`, `과목 식별 불명`을 구분합니다. 목록에서 빠졌다는 이유로 미개설을 판정하려면 해당 과목을 포함하는 캠퍼스·학기의 목록이 완전하다는 근거가 있어야 합니다. 미관측·식별 불명은 `k/n` 분모에서 제외하고 별도 표시합니다. 코드 변경과 동일·대체과목 관계에는 유효 기간과 근거 판본을 기록하고, 검증된 동일 과목 관계에 한해 개설 관측을 연결합니다.
- **시점 재현 평가:** rolling-origin의 각 예측 기준 시점에 공개되고 검수가 끝난 판본만 사용합니다. 이후 정정·취소는 해당 시점의 입력에 소급 적용하지 않습니다. 같은 시즌 개설 빈도와 직전 같은 시즌 관측을 기준선으로 비교하고, 제공률·보류율·판정 오류를 캠퍼스·시즌별로 남깁니다. 행사 예상 구간은 적중률과 구간 폭을 함께 기록합니다. 운영 기준은 검수 골드셋의 관측 범위와 재현 결과로 정합니다. [#41](https://github.com/ot4562-glitch/Hanmo_develop/issues/41)
- **반복 학사행사:** `campus-assist/activities.ts`가 제공하는 행사 계열(교내 학사 행사/전공 신청/졸업시험 등)의 과거 개최일을 연도별·공식 원문별로 묶습니다. 서로 다른 **최소 2개 연도**의 유효한 개최 근거가 있어야만 계절성 구간을 추정합니다. 현행 이식 코어는 개최일 분산 **45일 초과 시 보류**, 전후 **약 7일 여유**의 대략적 기간을 생성하는 휴리스틱입니다. 이는 학교의 공식 예정일/신청 시작·마감일이 아닙니다.
- **정정/취소 우선:** 해당 연도의 검증된 일정·취소·정정이 예측보다 우선합니다. 날짜 없는 취소가 어느 회차를 가리키는지 불명확하면 예측을 중단합니다. 출처 권리·검증일·대상 계열·과거 연도 간 충돌을 확인해야 하며, 자료가 불충분할 때 인위적인 D-day를 만들지 않습니다.
- **학생 표시:** `확정된 행사일`, `과거 이력 기반 예상 구간`, `근거 부족/취소 확인 필요`를 다른 시각/문구로 보여줍니다. 예상 구간에는 신청 버튼·확정 마감 알림을 연결하지 않고 공식 공지를 확인하도록 유도합니다.

### 4.6 근거 중심 학사 FAQ·교내 학사 상담 안내

- **검색:** 학교에서 재사용이 허용되고 검수가 끝난 한국어 FAQ·공지 문단을 문서 ID·개정 판본·문단 ID·적용 범위·검수 시각으로 연결합니다. 첫 학생용 검색은 브라우저의 **BM25 문자 bigram**을 기준으로 근거 문단·원문 링크·적용 조건·검수일을 보여주는 추출형 검색입니다. 약칭 사전과 질의 정규화가 기준선 대비 개선되는지 검증한 뒤 적용합니다. 서버 검색은 정적 검색의 품질 또는 배포 크기 한계가 측정된 뒤 검토합니다.
- **통합 검색 범위·책임 (1차 P0):** NLP 실무 담당 **이의상**이 공지·강의·FAQ의 공통 한국어 질의 처리, 오타/띄어쓰기·약칭 정규화, 검색 의도 분류, 관련성 순위 및 검색 실패 UX의 품질 계약을 담당합니다([#53](https://github.com/ot4562-glitch/Hanmo_develop/issues/53)·[#40](https://github.com/ot4562-glitch/Hanmo_develop/issues/40)). 기존 FAQ BM25는 **기준선**으로 유지하며 승인된 학사자료 범위에서 확장합니다. 공지의 실제 대상·마감 분류는 [#51](https://github.com/ot4562-glitch/Hanmo_develop/issues/51), 강의 원장/동일과목 식별은 데이터 담당의 [#41](https://github.com/ot4562-glitch/Hanmo_develop/issues/41)·[#42](https://github.com/ot4562-glitch/Hanmo_develop/issues/42) 승인 결과에 의존합니다.
- **질의 처리·후보 순위(목표, 미연결):** 원본 검색어와 정규화 후보를 구분하고 조사·띄어쓰기·흔한 오타·약칭을 처리하되 **학수번호·학번·날짜·고유명사는 임의로 고쳐 확정하지 않습니다**. `공지/강의/FAQ/불명확` 의도를 분류하되 불확실하면 복수 분야·원래 검색어로 다시 찾을 수 있어야 합니다. 승인 스냅샷의 출처·판본·캠퍼스·입학년도·전공·학기 조건을 우선 적용하고, 강의는 학수번호 정확 일치 → 과목명/교수 표시명 검색, 공지·FAQ는 제목/문단 BM25 문자 bigram을 기준선으로 후보 검색·순위화합니다. 유사도만으로 학생 적용 대상·이수 자격·마감을 확정하지 않고 부적합/철회 근거는 `확인 필요`로 보류합니다.
- **출시 품질 게이트 (초기 목표, 실측값 아님):** [#40](https://github.com/ot4562-glitch/Hanmo_develop/issues/40)의 사람이 검수한 골드셋은 공지·강의·FAQ와 정상/띄어쓰기/오타/약칭/복합질문/부정·예외/무관·답변불가 하위집합을 포함합니다. 문서 계열·판본·학기를 기준으로 튜닝/홀드아웃을 분리하고 **Recall@5 ≥ 0.90, MRR ≥ 0.80, 의도 분류 macro-F1 ≥ 0.90**, 오타·띄어쓰기 하위집합 Recall@5는 정상 대비 하락 **5%p 이내**를 초기 출시 목표로 합니다. 합의된 Windows PC Chrome/Edge 환경에서 **p95 검색 지연 300ms 이내**를 목표로 계측하고 코퍼스 규모·기기 사양을 기록합니다. **타 캠퍼스/학번 적용 확정, 미근거 학생 마감, 철회·미승인 근거 노출은 검증 세트에서 0건**이어야 합니다. 자료가 없거나 미측정/미달이면 통합 검색 공개를 보류하고 현재의 참고 목록·원문 안내를 유지합니다. 위 수치는 제품의 목표 기준이며 현재 달성 결과나 성능 보증이 아닙니다.
- **사람 검수 평가셋:** 캠퍼스·입학년도·전공별 질문, 약칭·띄어쓰기·오타, 부정·예외, 정정·취소, 답변 불가 사례를 수록합니다. 질문마다 근거 판본·문단 ID와 기대 답변 또는 보류 상태를 사람이 지정하고, 튜닝과 최종 평가를 문서 계열·판본 단위로 나눕니다. ### 5.1 마지막 과목 신청 실패 대응 · 대체과목 검색/시간 충돌 보류

**제거된 범위:** 이전 `LAST_VALID`의 합성 1·2·3번 후보 검색 및 `LAST_CONFLICT`의 번호 충돌 코드는 제거합니다. **남은 `LAST_VALID`는 실패 상태 안내만 제공**하고 대체과목을 자동 제안·선택하지 않습니다. `RECONNECT`의 0~6초 가상 404, 새로고침/뒤로가기 복귀, 짧은 세션 상태 복원은 유지하되 구버전의 후보 선택 세션은 복원하지 않습니다.

**재검토 조건:** 다음 수강신청 관련 기간에 활용 가능한 개설·분반/요일·시간 자료의 취득 경로를 확인하고, 학교의 자료 접근·재사용 허가(#27), 원문/판본 독립 검수(#41·#42), 실제 수강신청 UI 기준선 및 SELECT 대기열/Enter 동작 QA(#19·#71)를 확보한 뒤 **별도 승인**으로 재개 여부를 결정합니다. 단순 수강신청기간 도래가 곧 권리 확인·연동 허가가 되는 것은 아닙니다. 부정확한 ‘대체 가능’ 안내를 제공해야 한다면 기능을 재개하지 않습니다.

### 5.2 가상 404·새로고침·뒤로가기 (RECONNECT)

- `RECONNECT`가 ON인 가상 연습을 시작하면 **0~6초 사이**에 `404 예시화면 입니다`가 표시됩니다. **실제 HTTP 404를 반환하거나 통신을 끊지 않습니다**.
- 예시 화면의 새로고침·뒤로가기 선택으로 **진행 중이던 가상 수강신청을 이어서 수행**할 수 있습니다. 브라우저 새로고침 복원을 위해 `sessionStorage`의 짧은 수명 합성 상태만 사용합니다. 새 방문 시 설정은 다시 모두 OFF입니다.
- 재접속이 실제 신청 성공을 보장하거나 미확정 결과를 성공으로 바꾸지 않습니다. 학교 사이트·SSO·사용자 성적/학적 데이터에 연결하지 않습니다.
- 이후 대기열 지연·취소 실수·난이도별 복기 등의 확장은 **현재 UI 동결 범위를 넘어서는 선택 작업**이며 별도 우선순위 결정 전까지 구현을 요구하지 않습니다.

**평가 경계:** 현재 UI는 위의 합성 단계만 구현한 상태이며, 복잡한 상태전이/난이도 점수/학생 실기기 QA가 모두 완료됐다는 뜻이 아닙니다.

**시뮬레이션과 실제 강의의 경계:** 가상 수강신청 과목 코드와 공식 과목/분반 ID 사이의 연결은 명시적인 변환 계약으로만 수행합니다. 연습의 성공·취소·대기열은 실제 수강 확정이나 학점 취득을 뜻하지 않으며 이수 원장에 반영하거나 학교 시스템으로 전송하지 않습니다.

변환은 버전이 있는 표에 근거한 조회로 한정합니다. 가상 과목 ID에 대응하는 확인된 학교 과목·분반 ID가 없으면 `UNMAPPED`를 반환합니다. 1차 코어와 연결할 때는 브라우저용으로 빌드된 JavaScript 공개 계약만 사용합니다. [#22](https://github.com/ot4562-glitch/Hanmo_develop/issues/22) · [#62](https://github.com/ot4562-glitch/Hanmo_develop/issues/62)

### 5.3 시나리오 런타임 계약·회귀 기준 (#19·#20·#21·#22·#37)

**공통 계약:** 기존 한모의 `practiceSetter=1/2/3`은 각각 BASIC/TIME/SELECT입니다(`js/practice.js`). 원래 `js/practice.js`는 `TIMEtime`, `SELECTtime`, `SELECTWaitTime`을 초기화하고, `js/selectZone.js`의 `registerClick(val)`→대기열→`saveSugang(val)`이 모의신청을 처리하며, `js/result.js`가 시간을 요약합니다. **상태를 변경하는 훅은 승인된 실습 이벤트에만 두고, 시나리오가 OFF이면 기존 함수·키보드·타이머·결과 저장 경로와 호출 순서를 보존합니다.** 별도 시나리오 상태 저장 키는 `hanmo.practice.scenario.v1.*`처럼 학업 키와도 분리합니다. 합성 이벤트와 실제 신청·학점 원장은 연결하지 않습니다.

| 시나리오 | 시작·입력/상태 전이 | 종료/금지 |
|---|---|---|
| `LAST_COURSE_FAIL` | **현행 범위:** `READY → LAST_REJECTED → VERIFY_STATUS / UNRESOLVED`의 합성 실패·확인 동작을 우선 검증. **이전 설계의 `SEARCH_ALTERNATIVE → REPLACED / NO_VALID_ALTERNATIVE` 흐름은 후속 보류** | 실제 대체분반 검색·시간/학점/선수 제약 자동 판정을 2차 완료 조건으로 삼지 않음; 미확인 결과의 자동 성공/재신청 금지 |
| `RECONNECT_RECOVERY` | `ACTIVE → REQUEST_SENT → VIRTUAL_DROP → RECONNECT_QUEUE → RECONCILE → CONFIRMED / NOT_APPLIED / UNKNOWN` | 첫 버전 단절점은 **모의 신청 직후**. `UNKNOWN`은 수강 성공도 실패도 아니며 중복 재신청·자동 성공 금지. 합성 재입장·대기열만 사용하고 실제 네트워크·학교 인증·SSO를 조작하지 않음 |
| **조합 설정(현행)** | `LAST_VALID`·`RECONNECT` 둘을 각각 또는 동시에 선택할 수 있습니다. 대체과목 검색·시간 충돌 관련 설정/버튼/상태는 없음 | 기본 OFF이면 원래 `practice.html` 경로, ON이면 메뉴 안의 합성 훈련. 실강좌·실제 학교 네트워크와 연결하지 않음 |

**미래 확장용 고정 시나리오 입력 DTO(설계 전용, 현행 SETTING 사용자 입력 아님):** `{schemaVersion:1,scenarioId,scenarioSeed,mode,syntheticCourseIds,virtualClockStart,scenarioEnabled}`. 결과는 `{scenarioId,scenarioSeed,terminalState,actions,errors,elapsedVirtualMs,duplicateAttempts,source:'SYNTHETIC'}`이며 학업 원장 API/학교 네트워크로 전달하지 않습니다. 고정 시드와 입력은 **동일한 사건·상태 전이·결과**를 생성해야 합니다. 기존 대기열의 `Math.random()` 표현 및 실제 벽시계 UI를 그대로 통제했다고 가정하지 말고, 신규 시나리오의 의사난수·가상 시간만 분리해 주입합니다. 테스트에서는 랜덤 애니메이션 프레임을 비교하지 않고 정규화한 이벤트·저장 키·결과 상태를 비교합니다.

**난이도 및 평가(현행 범위):** 첫 검증은 마지막 과목 실패 시 결과를 성급히 성공으로 간주하지 않는지, 재접속 후 신청 상태를 확인하는지, 중복 신청을 피하는지, 정상 BASIC/TIME/SELECT 조작을 보존하는지에 집중합니다. **대체과목 적합성/시간 충돌/대안 없음 판정·복합 난이도 점수는 보류된 확장 범위**이며 해당 기능의 실행·사용성 결과 없이 출시 완료로 계산하지 않습니다.

## 7. 3차 — Supabase 설계·인계 및 실제 제품 연계

**아래는 목표 아키텍처이며 Supabase 프로젝트·자동 수집·DB 연동은 아직 구축하지 않았습니다.** 2026-11-19 사용자 확인에 따라 **Supabase는 Free 플랜($0) 범위에서만 운영**하고, **임창용 님이 프로젝트·계정·운영을 관리**하며, **장애 발생 시 개발팀이 함께 신속히 진단·복구**합니다. 유료 플랜 전환·유료 애드온·초과 사용료가 발생하는 서비스는 제품 설계 범위에서 제외합니다. 실제 계정 접근권·보안 키·복구 연락망은 프로젝트 생성 시 점검하되 운영 책임자를 다시 미정으로 취급하지 않습니다. 학사 원문 PDF/HTML/첨부파일을 DB에 통째로 저장하지 않고 권한이 확인된 **구조화 정보·근거 링크·필수 변경 이력**만 관리합니다.

**3차는 두 개의 완료 게이트를 구분합니다.** 우리 팀의 **설계 인계 완료**와 운영 책임자의 **실제 Supabase 연동·검증 완료**는 별개입니다. 4차로 진행하려면 검수된 자료가 실제 DB→읽기 API→학업 화면으로 전달되고, 정정·취소·권한·장애 대체·롤백과 기존 한모 시나리오까지 전체 제품 검증이 끝나야 합니다. 3차에서 1차 TypeScript·2차 JavaScript를 유지합니다.

### 7.2 데이터 갱신 아키텍처

```text
공식 공개 학사자료 또는 허가된 API
  → 정기 수집(GitHub Actions / 승인된 워커)
  → 원문 식별자·수정일·해시로 변경 감지
  → JSON/CSV 핵심 필드 정규화와 규정·일정 검증
  → 검수·승인 → 현재값 및 필요한 이력 DB 반영
  → 공개 읽기 전용 API → 학업 플랫폼
```

학교가 공식 API 또는 자동 수집 권한을 제공하지 않는 경우 **실시간 자동 갱신을 보장하지 않습니다**. 오류·누락·취소·정정에 대비해 확인 시각, 보류 표시, 재시도와 **정적 JSON 대체 경로**를 둡니다.

허용된 출처만 정해진 주기로 확인하며 재시도 후에도 실패하면 운영자가 처리합니다. 학생은 로그인 없이 **승인된 공통 학사자료만** 읽습니다. 수집·검수·승인 쓰기 권한을 분리하고 관리 키는 운영 환경에만 둡니다. 지연·장애 시 마지막으로 검수한 자료가 여전히 유효하면 확인 날짜와 함께 제공하고, 유효한 자료가 없으면 ‘확인 필요’와 확인 가능한 원문을 안내합니다. 개인 캠퍼스·전공 선택, 이수 원장, 성적, 수강계획과 체크 상태는 브라우저에 보관합니다. 학교 계정·인증 정보 및 학생의 원본 입력을 공통 자료 DB에 전송하는 경로는 두지 않습니다. 개인 동기화는 이 범위에서 제외하며 로컬 백업·내보내기·삭제는 §4.8을 따릅니다. ### 7.4 학교 회신 전 확정할 데이터·배포 경계 (#30·#31·#32)

**설계 대안과 선택:** (A) 1차부터 브라우저가 임의의 원문·Supabase 내부 테이블을 조회하는 방식은 권리 불명 자료 노출, 검수 우회, 판본 불일치 위험으로 채택하지 않습니다. (B) **1차는 검수된 불변 정적 스냅샷만 조회하고, 3차는 같은 스냅샷 계약을 Supabase의 승인된 공개 읽기 경로로 제공**하는 방식을 채택합니다. 실제 자동 수집·DB 계정·실환경 연결은 허가와 관리자 합의가 이루어진 뒤 시작합니다.

**논리 ID와 검수된 공개 릴리스 계약:**

| 구성 | 키/관계(설계) | 무결성·버전 조건 |
|---|---|---|
| 출처·사용권 | `sourceId`, 관할·원문 URL·권리 범위·확인일 | 사용권 상태 `UNKNOWN/ALLOWED/LIMITED/DENIED/REVOKED`; 권리 미확정 상태로 자동 수집·원문 재배포 금지 |
| 강의·개설/분반 | `courseId`, `termId`, `campus`, `offeringId`, `sectionId`, `sourceRevisionId` | 동일 과목·학기 중복 및 빈 관측 구분; 완전성이 입증되지 않으면 미개설 확정 금지 |
| 공지·이벤트 | `noticeId`, `revisionId`, `eventOccurrenceId`, `sourceId` | 게시·시작·학생 마감·행정 마감·정정/취소 분리; 수정하면 새 불변 판본을 생성 |
| 학칙·요건 | `rulePackId`, `requirementId`, `semanticKey`, `validFrom/To` | 캠퍼스·입학년도·전공/트랙·시행일이 충돌하면 선택 보류 |
| 검수·승인 | `sourceRevisionId`, `contentSha256`, `reviewerId`, `approverId` | **동일인 검수·승인 불가**, `APPROVED` 자체 문자열은 권한 증거 아님; 철회/권리변경 이력을 분리 |
| 정적·API 스냅샷 | `snapshotId`, `manifestSha256`, `publishedAt`, `revokedAt`, `schemaVersion`, `faqIndexRevision` | 공지·개설·FAQ가 **동일한 승인 스냅샷**을 가리켜야 공개; 불변 발행 뒤 포인터만 교체 |

실제 SQL에서는 외래키·유니크/중복방지 키, `sourceId+sourceRevisionId`, `snapshotId+documentId`, `campus+termId+courseId` 조회 인덱스, 게시/적용 시간 범위를 점검합니다. **업데이트는 기존 검수 판본 덮어쓰기보다 새 불변 판본 + 활성 포인터 교체**를 우선합니다. 중단/롤백은 승인된 직전 유효 스냅샷으로만 가능하며 **권리 철회·취소·중대한 정정**이 있는 구판을 자동 되살리지 않습니다. 물리 SQL/권한·인덱스 실행계획과 용량 수치는 [#64](https://github.com/ot4562-glitch/Hanmo_develop/issues/64)에서 실제 환경이 허가된 뒤 확정합니다.

**수집/갱신 상태 머신:** `PERMISSION_CHECK → FETCH(승인 출처만) → NORMALIZE → QUARANTINE → REVIEW → INDEPENDENT_APPROVAL → PUBLISH → MONITOR`. 실패/충돌/중복/권리 불명은 `QUARANTINE`으로 되돌리고, 취소·철회는 `REVOKED`로 공개 연결을 무효화합니다. 학교가 정기 접근을 허용하기 전에는 `FETCH`를 실행하지 않습니다. 허용된 뒤에도 출처별 최소 필요 주기·조건부 요청·지수 백오프·상한 재시도·수동 실패 큐를 사용하며 **실제 호출 주기와 쿼터는 허가 회신 및 계측 후** 정합니다. API 장애의 대체는 `schemaVersion`, `snapshotId`, 권리/유효성·최종 검수 시각이 확인되는 정적 파일만 허용합니다. 안전한 대체가 없으면 ‘자료 확인 필요’로 표시합니다.

**공개 읽기/API 및 RLS:** 학생에게는 별도 로그인이 없는 **승인·비철회 공통 학사 데이터 읽기**만 제공하며 관리자 테이블·원장·검수 원문·학생 성적은 Data API에 노출하지 않습니다. 공개 스키마에 테이블을 두는 경우 **RLS 활성화 + 최소 `GRANT` + 공개 데이터에 한정된 `SELECT` 정책**을 모두 확인합니다. 공개 뷰는 무조건 RLS가 적용된다고 믿지 않고 PostgreSQL 버전에 맞춰 `security_invoker` 또는 비공개 스키마/명시 권한 구성을 검증합니다. API 키는 공개 브라우저용 **publishable key**와 서버 비밀키를 구분하고 `service_role`/secret 수집키를 HTML/JS/GitHub Pages/정적 ZIP에 넣지 않습니다. `SECURITY DEFINER`를 간단한 권한 우회책으로 도입하지 않습니다. `anon` 쓰기·검수/승인·취소 API는 기본 거부하며 브라우저의 출처 문자열 또는 클라이언트 JWT 사용자 메타데이터를 검수 권한 증거로 사용하지 않습니다. [Supabase RLS 공식 지침](https://supabase.com/docs/guides/database/postgres/row-level-security) · [API 키 안내](https://supabase.com/docs/guides/getting-started/api-keys)

**개인정보/비용 경계:** 캠퍼스·전공 선택, 개인 이수/계획/체크 내역은 로컬 기본값으로 유지합니다. 서버에는 공통 공개 스냅샷 조회만 허용하며 개인 원본 업로드·선택형 동기화·학교 로그인 인증은 3차 기본 기능이 아닙니다. **월 지출 목표/상한은 $0(Supabase Free만 사용)으로 확정**하되, DB/인덱스·전송량·성장률의 실측 전에는 학교 전체 자료 수용량이나 처리 가능 사용자 수를 약속하지 않습니다. 무료 제한에 근접하면 유료 업그레이드 대신 자동 추가 수집을 중단하고 저장량·조회량 최적화 및 검수된 정적 스냅샷 대체를 사용합니다.

## 8. 4차 — JavaScript 소스 통합 전환

**착수 조건:** 1·2차 기능과 3차 Supabase 실제 연동이 승인된 배포 환경에서 안정적으로 작동하고, 자료 출처/권리·검수·보안·성능·접근성·기존 시뮬레이터 회귀 검증을 통과해야 합니다. 설계 문서 인계나 합성 데이터 시연은 착수 조건이 아닙니다.

- **대상:** 1차의 TypeScript 계산 코어·브라우저 진입점·관련 테스트를 **동일 기능의 JavaScript + JSDoc**으로 기능별 순차 이관합니다. 2차의 기존 JavaScript·HTML/CSS는 유지하고 React 화면은 도입하지 않습니다.
- **품질 유지:** `checkJs` 등 정적 검사, 런타임 입력 스키마 검증, 단위·속성·실제 브라우저 회귀 검증을 유지합니다. 같은 입력·같은 학칙/자료 판본을 이전 TypeScript 구현과 새 JavaScript 구현에 넣어 결과·예외·`NEEDS_REVIEW` 상태가 일치하는지 차등 테스트합니다.
- **기존 데이터 보호:** 학점·요건·공지 ID, API/스냅샷 버전, 로컬 저장 형식, Supabase 읽기 전용 데이터 계약을 유지합니다. 필요 변경은 명시적 버전 마이그레이션·복구 경로를 검증합니다.
- **이관 방식:** 작고 검토 가능한 PR 단위로 원본 소스와 테스트를 함께 옮기며, 검증 전에는 TypeScript 기준 구현을 보존합니다. 빌드된 JavaScript 파일을 직접 편집하는 것은 소스 이관으로 보지 않습니다.
- **전환 순서와 기준 범위:** 현재 `js/academic/` 구조를 기준으로 입력·출력 스키마와 JSDoc 타입 → `core/academics/`, `core/forecast/`, `core/campus-assist/` 및 공지·학사일정 코어와 해당 `*.test.ts` → `views/`와 `app/`의 `main.ts`, `catalog.ts`, `academic-timeline.ts` 및 관련 자료 → 정적 검사·번들 설정 순으로 전환합니다. 입력 스키마와 코어가 먼저 있어야 화면을 전환할 수 있습니다. 확정된 릴리스 소스를 기준으로 분할 PR별 의존성을 대조합니다.
